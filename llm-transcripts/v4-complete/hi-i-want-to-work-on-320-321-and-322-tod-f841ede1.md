### feedback_cross_language_pitfalls.md

```markdown
---
name: Cross-language design pitfalls
description: Three approaches the user rejected when designing SoraMech's cross-language wire format
type: feedback
originSessionId: e9ed70c7-2b63-425c-987c-6431040bedfb
---
When designing anything that touches the cross-language data path, avoid these three shapes — the user pushed back on each and the rejections are load-bearing for the architecture.

**1. Don't propose runtime "handles" that route operations back to the originating spec.**

**Why:** Real library functions in the wild (qsort, libcurl, anything from libc) expect actual native values — a real `int (*)(int,int)` function pointer, a real `char *` — not a SoraMech-issued id string. They can't be modified to participate in our runtime's routing scheme. The wire must carry data the destination spec can fully reconstruct into a native value, not opaque tokens.

**How to apply:** When a value seems hard to serialize (function pointers, coroutines, opaque pointers), decompose to data primitives (address + signature, bytecode + upvalues, ptr + length). If the destination needs a callable, the destination spec synthesizes one at reconstruction time (libffi trampoline for C, `ffi.cast` for LuaJIT). The "phone home" callback that the trampoline performs internally is fine — it's an artifact of the destination spec's reconstruction, not exposed in the wire format. What's forbidden is a wire primitive that says "operations on this value cross back to the source."

**2. Don't propose pair-wise language conversion paths (lua→c, c→lua, etc.).**

**Why:** N languages means N² conversion paths, which means adding a new language breaks the existing ones. The wire must use a language-agnostic intermediate (JSON) and every spec must implement only the two pair-symmetric callbacks (`to_json`, `from_json`). New language = implement those two functions, nothing else touches.

**How to apply:** Never write code that names two specific languages in a conversion context. Specs only ever see JSON on the wire. If a JSON primitive needs an extension (like `$function_pointer`), it lives in the universal JSON contract, not as a lua-spec-specific or c-spec-specific concept.

**3. Don't propose per-function annotations for type ambiguities (lengths, discriminators, callback signatures).**

**Why:** The user pointed out that "discriminator" is a vocab word the system has no general way to ask about. We can't prompt "which param is the length?" because that pairing convention lives in the function's English documentation, not its types. Asking the user to write annotations means asking them to know specialized vocabulary they didn't sign up for.

**How to apply:** When a function signature has ambiguous types (`char *` with no length, `union` with no tag, `void *` with no signature), expose each parameter as a separate input slot on the box. The user wires the slots according to the function's documentation — `p` from one source, `n` from another. The system never infers pairings; the user expresses them by wiring. If the destination needs a length and no length wire is provided, the wire compile fails with a plain-English fix-it message ("destination needs length, source provides only a pointer — wire a length input here").

**Common thread:** all three rejections are the same principle in different clothes — **SoraMech bends to the language, not the other way around.** Users write idiomatic code in their language. Libraries are used as-is. Specs are self-contained and pair-symmetric. The system stays out of the user's vocabulary.
```

### project_cross_language_wire.md

```markdown
---
name: Cross-language wire format
description: Dual-ring slot per port (native ring + JSON ring + ordering ring). JSON only at language borders. Per-edge classification at graph load; per-cell precision at runtime.
type: project
originSessionId: 5670858b-274f-49c4-89b8-a4b83ce33d7c
---
Design corrected 2026-05-21 — replaces the older "JSON always" framing.

**Each input slot is a dual-ring buffer.** Per port: one `ring_native` (consumer-language native bytes), one `ring_json` (JSON bytes from cross-language producers), and one `ring_order` of `(which_ring, idx)` tuples in arrival order. Allocate `ring_json` and `ring_order` lazily — same-language-only ports pay nothing for them.

**Push selects ring by per-edge bit.** Producer's spec writes native bytes to `ring_native` if `output_edge_native[j]` is true; otherwise calls `native_to_json` and writes to `ring_json`. Either way, pushes a `(which_ring, idx)` tuple to `ring_order`.

**Pop reads ordering ring first.** Dispatch pops `ring_order`, gets `(which_ring, idx)`, then pops the indicated cell. The consumer's spec receives `(input_data[i], input_native[i])` per input port and dispatches per flag — decode native or decode JSON.

**Why dual-ring instead of per-port classification.** Per-port (slot is all-JSON if any fan-in is cross-lang) is the pessimistic approximation — same-language values eat JSON cost on mixed-fan-in ports. Dual-ring is precise per cell: a port fed by one Lua box and one C box keeps the Lua cells native and JSON-encodes only the C-sourced cells.

**Why JSON for the cross-language ring (not pair-wise paths, not type-annotated raw bytes).** JSON's structure is self-describing — every language has a natural mapping for object/array/number/string/bool/null. Adding language K means K's spec implements its own `native_to_json` and `json_to_native`. N spec-pairs, not N² language-pair paths. The native ring's format is each spec's private choice — Lua may pick msgpack or `cjson.encode` or a custom binary form; C uses `memcpy` of the wrapper struct; Bash uses strings.

**Sentinel primitives for non-JSON-mappable values.** `$ref` (pointer + length into the large-value heap), `$function_pointer`, `$lang_opaque` ("these bytes are language-X-internal"). Carried inside the JSON ring as object-shaped sentinels. Cross-language receivers that can't reconstruct fail at wire compile.

**`$function_pointer` reconstruction — wrapper binary + persistent subprocess (issue 318, amended 2026-05-22).** Earlier design had the consumer's spec FFI-cast the raw process-local address. Rejected: FFI is language-pair-specific, biases SoraMech toward the Lua↔C corner, breaks the N-not-N² rule. Replacement: at map-compile time the compiler asks the *producing* spec to compile the referenced function + its enumerable dependencies into a standalone wrapper binary on disk that speaks a small line protocol on stdio. The consumer spec spawns one persistent subprocess per `$function_pointer` it receives and talks to it over the same socket-like channel used for any out-of-process spec. Every language pays the same price; new languages only implement "compile a function to a wrapper binary" — no pair-wise FFI knowledge required.

**Spec `invoke` signature change.** Collapses `invoke_native` and `invoke_json` into one `invoke` with per-input/per-output flags: `int invoke(handle, ..., const int *input_native, int n_inputs, int output_native, void *out_buf, ...)`. The spec dispatches per input internally. This is the contract change that unblocks 306/307's typed marshalling.

**Two compile-time layers stack:**
- **Per-edge classification (issue 312, this design)** — graph loader computes `input_edge_native[]` and `output_edge_native[]` on each box; dispatch routes pushes accordingly. This issue is the wire-format design.
- **Same-language source merge (issue 313, research / blocked)** — concatenate every same-language box's source into one translation unit per language. Boxes still run as separate thread-pool tasks; what 313 thins is the spec invocation overhead inside the merged region (direct call into the worker's `lua_State` instead of dlsym + marshal + bridge). The dual-ring slot machinery does NOT collapse — tasks still need slots to wait for sibling inputs. 313 makes the ring cells cheaper to read/write; it doesn't remove them.

**Three rejected design shapes** (kept here so they don't get reinvented):
1. **Handles back-routing to the owning spec** — library functions in the wild can't be modified to use SoraMech-shaped handles. Rejected.
2. **Pair-wise language paths** — every new language would have to grow N-1 translation paths against existing languages. Rejected. The dual-ring's "two rings per slot" is the dimension-cap that prevents this.
3. **Per-function discriminator / length annotations on the wire** — the system has no universal vocabulary to ask "is param 2 the length?" Rejected; the user expresses these by wiring two separate input slots.

**How to apply:** When discussing wire format, slot store shape, dispatch routing, or spec callbacks: think dual-ring (native, JSON, ordering) per slot, per-edge classification at push time, per-cell tag at pop time, JSON-only-at-borders, language-private native bytes everywhere else.

```

```markdown
---
name: Custom translation specs per port
description: Users can override the default native/JSON wire path on any input port for any reason — a knob in the wire format vocabulary (issue 246)
type: project
originSessionId: 1228a221-1c09-4c26-94f3-172d7777b2b9
---
**Per-port custom translation specs** let the user intervene at a specific input port and replace the default dual-ring decode path with user-written code. The override applies to that one port; the rest of the graph uses the default native-or-JSON path from issue 312.

**Motivating cases (any reason qualifies, not just cross-language):**
- Cross-language ambiguity the default specs can't infer: a C++ class with methods landing at a C box (drop methods? expose as fn pointers? restructure?), a `void *` carrying a libcurl handle, a union whose discriminator is on a separate wire.
- Same-language reshape: massaging a value into a different shape on its way in (rename fields, drop a layer, project a subset) without adding a transform box on the canvas.
- Validation / coercion: clamp a number, enforce a schema, fail loudly on unexpected shapes.

**How it composes with the dual-ring design:**
- The custom spec runs at *pop* time on the consumer side, after the ordering ring has been consulted and the cell has been read from the appropriate ring. The user's code receives the decoded value (native or JSON-decoded) and produces whatever the consumer's `invoke` will see.
- A port with a custom translation gets its own wire color in the editor (issue 245) — visible signal that this port doesn't use the default path.

**Why:** The default native/JSON contract covers the cases JSON's structure handles cleanly. Everything outside that needs a user escape hatch — *and* the same hatch is useful for purely-local "I want this input shaped differently" cases. One mechanism, many uses.

**How to apply:** When the design needs an override knob on the cross-language path, propose "custom translation spec on the destination port" rather than inventing per-function annotations, type discriminator metadata, or producer-side conversion hints (all three were rejected — see feedback_cross_language_pitfalls). The port is the unit of override; the spec is user code; the rest stays default.
```

### project_threading.md

```markdown
---
name: threading_model
description: SoraMech's threading model — phase 2 synchronous, phase 3 SoraMech-owned C thread pool with per-port slots and language specs
type: project
originSessionId: 579d58b3-7452-44f3-983a-80ff5821082a
---
**Phase 2 (current)**: synchronous executor in `src/004-executor.lua`. Single-threaded, sequential box execution. One driver shell-out per box call. The phase 2 path goes away when phase 3 lands — no fallback, no coroutine intermediate.

**Phase 3 (designed, not yet built)**: C pool runner with a SoraMech-owned thread pool. The 3d-rts pool at `/home/ritz/programming/ai-stuff/games/3d-rts/libs/900-task-pool.h` is the **design reference**, not vendored — SoraMech owns its pool implementation so the spawn primitive, worker context, init barrier, and iterator-pinning extensions are all under our control. The architecture is fully specified across issues 301–313.

Key phase 3 concepts:
- **Per-input-port slots** (not per-task), allocated at graph load and durable for the run. Each slot is a ring buffer (`n_cells` cells of `cell_capacity` bytes). 1-cell slots use peek-not-drain (literals, single-push wires); N-cell slots use pop-and-drain (queued / multi-push wires). No per-slot refcounting — slot lifetime is the whole run.
- **Tasks are ephemeral**: spawned dynamically by the dispatch layer when a box's input set is ready. Tasks carry just `box_id` and a counter snapshot. Box state (counter, input slots, language handle) is durable.
- **Language specs** under `langs/<name>/spec.so`, loaded via `dlopen` at startup. Uniform `lang_spec_t`. No language is privileged.
- **Same-language fast path** (issue 312): wire format defaults to JSON, but two adjacent same-language boxes use the language's native serialization (Lua `lua_dump`, C struct memcpy). Compile-time wire classification picks the path.
- **In-process specs** (Lua, C) via `lua_pcall` / `dlsym`. **Out-of-process specs** (Bash) via Unix domain sockets to a persistent per-worker subprocess.
- **Dispatch layer** (304) is the worker-side action: pop inputs → branch on box mode → invoke spec → push to downstream input slots → end. No blocking, no wait lists; tasks spawn on input arrival and run to completion.
- **Iterator and comparator routing** in the dispatch layer. Comparator runs the function and routes by output value. Iterator skips the function and routes by per-box counter (atomic spawn-time increment). Iterator tasks parallelize across workers; ordering preserved via per-push counter tags on consumer slots.
- **No-null rule** (issue 230): every input port must be wired, given a literal, or marked optional. Compile fails on missing inputs.
- **Init barrier**: pool startup waits until every worker has run every spec's `init(worker_idx)` before submitting tasks. Avoids tasks landing on uninitialized handles.
- **Hard-crash error policy**: nonzero return from any spec aborts the program.
- **Blocking semantics**: long-running operations tie up a worker. Pool size is the budget. Cooperative split (kickoff + check-done iterator) avoids holding a worker. See `docs/004-ipc-and-threading.md`.

**Effil is explicitly NOT used.** Coroutines are not used. The C pool is the chosen mechanism. 3d-rts is referenced as design inspiration, not vendored.

**How to apply:** When discussing threading, parallelism, or cross-language IPC: phase 2 is synchronous shell-out drivers; phase 3 is the SoraMech-owned C pool runner with `lang_spec_t`, per-port slot stores, and dispatch-layer routing. Never suggest effil. 3d-rts is a reference, not a dependency. Issues 301–313 carry the design.
```

8	## Current behavior
9	
10	A box's identity is frozen at graph-load. The loader parses
11	`boxes/<id>.json` once, fills in every field — kind, language,
12	function pointer, input port list, routing shape, outgoing
13	connections — and the dispatch layer reads that record on every
14	fire. Nothing in the running program changes a box's record.
15	
16	Issue 319f already added a language-agnostic way to **create**
17	new boxes at runtime: the BOX_CREATE_BOX kind. A box of that
18	kind takes a JSON spec on a `spec` input port; when it fires, it
19	parses the spec, allocates the new box at a fresh graph slot,
20	and emits the new id as a string on its output wire. Downstream
21	consumers can take the id and wire the new box up further (via
22	BOX_CONNECT).
23	
24	This issue extends that pattern to **reconfigure** and
25	**delete** — also via a box kind, not via library functions in
26	the language bridges. The new mechanism is the utility-box: a
27	single box kind that subsumes create / reconfigure / delete by
28	inspecting the spec it receives.
29	
30	## Architectural ground rules (from the design discussion)
31	
32	1. **Graph mutation is a box-kind operation, not a language-
33	   bridge function.** Users express mutations by placing
34	   utility-boxes in their maps and wiring them, not by writing
35	   code that imports the runtime as a library. The runtime is
36	   the substrate; users express through it.
37	2. **Manual JSON construction is supported but not assisted.**
38	   A user who wants to build a long-running Lua box that
39	   accumulates JSON for its own future reconfigure can do so —
40	   the manual path works as long as the bytes end up on a wire
41	   that feeds a utility-box. We don't provide convenience
42	   helpers for this path; the box-and-wire path is the intended
43	   one.
44	3. **The wire endpoint is the target.** When a utility-box's
45	   output wire points at box X's input port, that wire IS the
46	   declaration of "this utility-box operates on box X." No
47	   separate target_id input.

49	   all the same kind, dispatched by the spec's content. Folds
50	   in 319f's BOX_CREATE_BOX.

52	   RING_RECONFIGURE.** No separate control queue. The gather
53	   lock makes peek-then-pop honest within the lock, so the
54	   peek-vs-pop race that would have plagued an unsynchronised
55	   design doesn't appear.

57	## The five structural pieces
58	
59	### 1. The utility-box kind
60	
61	One box kind absorbs 319f's BOX_CREATE_BOX. The behaviour
62	depends on the spec's content:
63	
64	- **Spec describes a box with no existing target** (or target
65	  doesn't exist in the graph): CREATE. Allocate at a fresh
66	  graph slot. Emit the new id as a string on the output wire.
67	- **Spec describes a box with an existing target id** (the
68	  wire's endpoint matches an existing box): RECONFIGURE.
69	  Build a replacement box struct. Push the struct pointer to
70	  the target box's input slot (whichever port the wire ends
71	  at), tagged RING_RECONFIGURE.
72	- **Spec is empty / minimal** (no fields, no function): DELETE
73	  signal. Push a delete-marker to the target box's input slot,
74	  tagged RING_DELETE (or maybe just RING_RECONFIGURE with a
75	  null struct — see open items).
76	
77	### 2. The gather flag
78	
79	Each box record carries one atomic int — the gather flag — with
80	two states:
81	
82	- **0 (free):** any worker may attempt to enter.
83	- **1 (held):** exactly one worker is currently in the gather
84	  section.
85	
86	Workers entering a box CAS from 0 to 1. Win → enter gather.
87	Lose → yield-and-requeue (push task back to pool tail and
88	return). No spinning, no blocking. Per-box, so workers on
89	different boxes don't contend.
90	
91	### 3. The graph slot as liveness indicator
92	
93	The graph stores boxes as an array of pointers, one per box id.
94	`graph_box(graph, id)` returns the current pointer. The mutator
95	atomically swaps that pointer from OLD to NEW. Workers that
96	LATER look up the same id get NEW; workers mid-fire on OLD
97	finish on OLD.
98	
99	A box is **live** when the graph slot points at it. **Superseded**
100	when the graph slot points at something else (or NULL, for
101	delete). The two-state flag doesn't need a third "redirect"
102	state because the graph slot itself is the source of truth for
103	"is this still the current box."
104	
105	### 4. The reference count
106	
107	Each box record has an atomic refcount. Workers increment at
108	the top of their fire (just after resolving the pointer through
109	the graph slot) and decrement at the bottom. The mutator
110	increments when it becomes the mutator, decrements after the
111	swap.
112	
113	Freeable when BOTH:
114	- Graph slot doesn't point at this box (superseded), AND
115	- Refcount has dropped to zero.
116	
117	Whoever decrements to zero AND observes the graph-slot
118	mismatch frees the box. Mutator's "hold a +1" discipline
119	ensures the refcount only reaches zero AFTER the mutator
120	finishes its work.
121	
122	### 5. The reconfigure tag on input slots
123	
124	Each input slot's ordering ring grows a RING_RECONFIGURE value
125	alongside the existing RING_NATIVE and RING_JSON. When a worker
126	enters gather and peeks each input port's ordering ring, a
127	RING_RECONFIGURE tag at any port's head means "this is a
128	control message, not a value." The cell holds a pointer to a
129	pre-built box_t struct (built by the utility-box during its
130	fire, in the utility-box's worker thread — no parsing happens

133	## The worker arrival flow

135	```
136	1. look up the graph slot for X → get current box pointer (B).
137	2. CAS B's gather flag from 0 to 1.
138	   - lose: yarq this task. exit.
139	   - win: continue.
140	3. increment B's refcount.

159	## The mutator flow
160	
161	```
162	1. with B's gather flag held and refcount +1:
163	2. pop the replacement struct pointer (call it NEW) from the
164	   RING_RECONFIGURE-tagged cell.
165	3. resolve NEW's input_slot_ids by port-name matching:
166	     for each port in NEW:

175	   slot store didn't change — get fired under the new shape
176	   when the requeued task runs.)
177	8. decrement OLD's refcount; free OLD + abandoned slots if 0.
178	```

```
1	# 321 — Unify connections-array mutation through the 320 box-swap path
2	
3	## Status
4	open · waits on 320 landing first; design is straightforward
5	once the box-swap mechanism exists
6	
7	## Current behavior
8	
9	Issue 319d added the ability to attach new outgoing connections
10	to an existing box at runtime via `runtime_connect`. The way it
11	does this today is a special-case atomic dance directly on the
12	box's `connections` field: allocate a new connections array,
13	copy the old entries, append the new entry, atomic-store the
14	pointer, then atomic-store the new count. Readers that walk
15	the connections array use the order "read count first, then
16	pointer" so they always observe either the old pair or the new
17	pair, never a torn mix.
18	
19	This works because the connections array is append-only —
20	runtime_connect only ever adds, never removes or reorders.
21	That's the reason the staggered-publish pattern doesn't break
22	existing readers.
23	
24	Once issue 320 lands, the runtime has a more general mechanism:
25	build a fully replacement box struct, push its pointer to the
26	target's control queue, let the next worker visit do the
27	atomic graph-slot swap. This mechanism is strictly more
28	powerful than the connections-only dance — it can change
29	anything about the box, not just append to one field.
30	
31	## Intended behavior
32	
33	Retire the special-case copy-and-publish on the connections
34	field. Re-implement `runtime_connect` as a thin wrapper over
35	`runtime_apply_box_spec`:
36	
37	1. Look up the current box for the target id.
38	2. Build a new box struct that is a copy of the current one,
39	   with the new connection appended to its connections array.
40	3. Call `runtime_apply_box_spec(target_id, new_spec_json)` (or
41	   the underlying push-pointer-to-control-queue equivalent).
42	
43	The atomic discipline collapses to one path. The connections
44	field on `box_t` can become a plain pointer + plain int (no
45	`_Atomic` qualifiers needed) because the only way to mutate it
46	is via the box-swap mechanism, which never modifies a live box
47	in place.
48	
49	## Why bother
50	
51	- **One mutation discipline instead of two.** Every change to
52	  a box's identity — adding a connection, changing the function
53	  pointer, renaming a port, deleting the box — uses the same
54	  build-new-and-swap pattern. Less code to maintain, fewer
55	  edge cases to learn.
56	- **The connections-only dance is structurally fragile.** It
57	  relies on append-only semantics that nobody enforces at the
58	  type level. A future change that wanted to remove or reorder
59	  connections would silently introduce torn-read bugs. Removing
60	  the path removes the trap.
61	- **Smaller box_t.** The `_Atomic` qualifiers on
62	  `n_connections` and `connections` can come off. Plain int +
63	  plain pointer is fine because mutation only happens during
64	  the build-new step, before the new box is published.
65	
66	## Suggested implementation steps
67	
68	1. **Re-implement `runtime_connect` as a wrapper over
69	   `runtime_apply_box_spec`.** Caller still sees the same
70	   signature; internals route through the box-swap path.
71	2. **Remove the `_Atomic` qualifiers on `n_connections` and
72	   `connections` in `src/010-graph-loader.h`.** Plain types
73	   suffice now.
74	3. **Remove the copy-and-publish helper in
75	   `src/010-graph-loader.c`** that runtime_connect used to
76	   call.
77	4. **Verify the existing 319d fixture (`319d-runtime-create`,
78	   `319e-c-create`, etc.) still passes under the new path.**
79	   The behavioural contract for runtime_connect is unchanged;
80	   the internal mechanism changes.
81

85	  copy-and-publish helper.

89	  guard; no new fixtures needed.
```

1	# 322 — Box delete: the user-facing experience
2	
3	## Status
4	open · the underlying mechanism is part of 320; this issue
5	covers the user-facing API and the explicit-vs-implicit-deletion
6	design decision
7	
8	## Current behavior
9	
10	Once issue 320 lands, the runtime has a unified
11	`runtime_apply_box_spec(target_id, spec_json)` entry point that
12	handles create / reconfigure / delete based on the spec's
13	content. The delete path is: install NULL at the graph slot
14	via the same supersession mechanism, let the refcount drive
15	the old box's eventual free.
16	
17	What 320 does NOT cover, and what this issue is for:
18	
19	- The user-facing spec shape that triggers deletion.
20	- A convenience wrapper for the common case.
21	- Validation that catches "I forgot to fill in fields"
22	  accidents from masquerading as deletes.
23	- The downstream effects when consumers wired to a deleted box
24	  try to push values into the now-gone graph slot.
25	
26	## Why deletion needs more than just "any minimum spec"
27	
28	The natural shortcut would be: "if the spec only has an id and
29	no other fields, treat it as a delete." Compact and elegant.
30	
31	But it's also dangerous: a user who forgets to populate fields
32	in their reconfigure spec accidentally deletes the box. Defaults
33	should fail-closed (do nothing surprising) rather than fail-open
34	(do something destructive). The minimum-spec-means-delete shape
35	fails open.
36	
37	The safer alternative is an explicit marker in the spec:
38	
39	```json
40	{"action": "delete", "id": "target_box_id"}
41	```
42	
43	The runtime parses the spec, sees `action == "delete"`, and
44	routes through the delete path. Specs without an explicit
45	`action` field default to create-or-reconfigure (the inferred
46	action based on whether target_id exists). Explicit beats
47	implicit; destructive operations are always explicit.
48	
49	## Convenience wrapper
50	
51	For the common case where a user just wants to delete a box
52	they know the id of, add a sugar function:
53	
54	```c
55	int runtime_destroy_box(const char *target_id, char **err_out);
56	```
57	
58	Internally, this constructs the delete spec JSON and calls
59	`runtime_apply_box_spec`. Same code path, friendlier signature.
60	
61	Same shape per language bridge:
62	
63	- Lua: `soramech.destroy_box(target_id)`
64	- C:   `soramech_destroy_box(target_id, err_buf, err_cap)`
65	- Bash: `soramech_destroy_box "$target_id"`
66	
67	## Downstream effects of deletion
68	
69	A box X is deleted. Some other box Y has a connection pointing
70	at X. Y fires, produces an output, attempts to push to X's
71	input slots — but X is gone from the graph slot.
72	
73	Two possible behaviours:
74	
75	- **Silent drop:** the push fails because the target lookup
76	  returns NULL. Producer continues; output is lost. A push
77	  event with `result=target-gone` records the loss in the
78	  JSONL transcript.
79	- **Hard error:** the push fails and the producer's fire is
80	  treated as a failure. The run aborts (or the producer's
81	  spec returns an error code).
82	
83	The user's stated preference throughout the project is "errors
84	over fallbacks." So hard error is the strict reading. But
85	deletion is a deliberate user action — if they deleted X, they
86	probably know Y depended on it. Hard-error-on-every-push would
87	mean a single deleted leaf-box could crash the entire run.
88	
89	A middle path: silent drop by default, with the JSONL event
90	making the loss observable, AND a runtime knob (env var or
91	spec field) to upgrade the drop to a hard error for users who
92	want strict behaviour.
93	
94	## Suggested implementation steps
95	
96	1. **Define the spec shape for delete.** `{"action": "delete",
97	   "id": "..."}`. Document that the `action` field defaults to
98	   "apply" (which means create-or-reconfigure based on target
99	   existence) and the only other recognised value is "delete".
100	2. **Implement the delete path inside
101	   `runtime_apply_box_spec`.** Already part of 320's
102	   implementation; this is just adding the action dispatch.
103	3. **Add `runtime_destroy_box` as the sugar wrapper.** Three
104	   language bridges plus the C entry point.
105	4. **Add the push-target-gone JSONL event.** Same shape as
106	   other push events; `result=target-gone` is the new value.
107	5. **Add an opt-in strict mode** for users who want push-to-
108	   deleted-box to hard-error rather than silent-drop. Env var
109	   `SORAMECH_STRICT_DELETE=1` or per-call flag, TBD.

113	     the push fails with `result=target-gone` in the JSONL.
114	   - `tests/maps/322-delete-and-recreate` — A box X is created,
115	     deleted, then created again with the same id and different
116	     behaviour. The recreate succeeds at the now-NULL graph

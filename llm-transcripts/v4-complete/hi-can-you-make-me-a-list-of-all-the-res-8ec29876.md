### feedback_cross_language_pitfalls.md

```markdown
---
name: Cross-language design pitfalls
description: Three approaches the user rejected when designing SoraMech's cross-language wire format
type: feedback
originSessionId: e9ed70c7-2b63-425c-987c-6431040bedfb
---
When designing anything that touches the cross-language data path, avoid these three shapes — the user pushed back on each and the rejections are load-bearing for the architecture.

**1. Don't propose runtime "handles" that route operations back to the originating spec.**

**Why:** Real library functions in the wild (qsort, libcurl, anything from libc) expect actual native values — a real `int (*)(int,int)` function pointer, a real `char *` — not a SoraMech-issued id string. They can't be modified to participate in our runtime's routing scheme. The wire must carry data the destination spec can fully reconstruct into a native value, not opaque tokens.

**How to apply:** When a value seems hard to serialize (function pointers, coroutines, opaque pointers), decompose to data primitives (address + signature, bytecode + upvalues, ptr + length). If the destination needs a callable, the destination spec synthesizes one at reconstruction time (libffi trampoline for C, `ffi.cast` for LuaJIT). The "phone home" callback that the trampoline performs internally is fine — it's an artifact of the destination spec's reconstruction, not exposed in the wire format. What's forbidden is a wire primitive that says "operations on this value cross back to the source."

**2. Don't propose pair-wise language conversion paths (lua→c, c→lua, etc.).**

**Why:** N languages means N² conversion paths, which means adding a new language breaks the existing ones. The wire must use a language-agnostic intermediate (JSON) and every spec must implement only the two pair-symmetric callbacks (`to_json`, `from_json`). New language = implement those two functions, nothing else touches.

**How to apply:** Never write code that names two specific languages in a conversion context. Specs only ever see JSON on the wire. If a JSON primitive needs an extension (like `$function_pointer`), it lives in the universal JSON contract, not as a lua-spec-specific or c-spec-specific concept.

**3. Don't propose per-function annotations for type ambiguities (lengths, discriminators, callback signatures).**

**Why:** The user pointed out that "discriminator" is a vocab word the system has no general way to ask about. We can't prompt "which param is the length?" because that pairing convention lives in the function's English documentation, not its types. Asking the user to write annotations means asking them to know specialized vocabulary they didn't sign up for.

**How to apply:** When a function signature has ambiguous types (`char *` with no length, `union` with no tag, `void *` with no signature), expose each parameter as a separate input slot on the box. The user wires the slots according to the function's documentation — `p` from one source, `n` from another. The system never infers pairings; the user expresses them by wiring. If the destination needs a length and no length wire is provided, the wire compile fails with a plain-English fix-it message ("destination needs length, source provides only a pointer — wire a length input here").

**Common thread:** all three rejections are the same principle in different clothes — **SoraMech bends to the language, not the other way around.** Users write idiomatic code in their language. Libraries are used as-is. Specs are self-contained and pair-symmetric. The system stays out of the user's vocabulary.
```

### project_cross_language_wire.md

```markdown
---
name: Cross-language wire format
description: Dual-ring slot per port (native ring + JSON ring + ordering ring). JSON only at language borders. Per-edge classification at graph load; per-cell precision at runtime.
type: project
originSessionId: 5670858b-274f-49c4-89b8-a4b83ce33d7c
---
Design corrected 2026-05-21 — replaces the older "JSON always" framing.

**Each input slot is a dual-ring buffer.** Per port: one `ring_native` (consumer-language native bytes), one `ring_json` (JSON bytes from cross-language producers), and one `ring_order` of `(which_ring, idx)` tuples in arrival order. Allocate `ring_json` and `ring_order` lazily — same-language-only ports pay nothing for them.

**Push selects ring by per-edge bit.** Producer's spec writes native bytes to `ring_native` if `output_edge_native[j]` is true; otherwise calls `native_to_json` and writes to `ring_json`. Either way, pushes a `(which_ring, idx)` tuple to `ring_order`.

**Pop reads ordering ring first.** Dispatch pops `ring_order`, gets `(which_ring, idx)`, then pops the indicated cell. The consumer's spec receives `(input_data[i], input_native[i])` per input port and dispatches per flag — decode native or decode JSON.

**Why dual-ring instead of per-port classification.** Per-port (slot is all-JSON if any fan-in is cross-lang) is the pessimistic approximation — same-language values eat JSON cost on mixed-fan-in ports. Dual-ring is precise per cell: a port fed by one Lua box and one C box keeps the Lua cells native and JSON-encodes only the C-sourced cells.

**Why JSON for the cross-language ring (not pair-wise paths, not type-annotated raw bytes).** JSON's structure is self-describing — every language has a natural mapping for object/array/number/string/bool/null. Adding language K means K's spec implements its own `native_to_json` and `json_to_native`. N spec-pairs, not N² language-pair paths. The native ring's format is each spec's private choice — Lua may pick msgpack or `cjson.encode` or a custom binary form; C uses `memcpy` of the wrapper struct; Bash uses strings.

**Sentinel primitives for non-JSON-mappable values.** `$ref` (pointer + length into the large-value heap), `$function_pointer`, `$lang_opaque` ("these bytes are language-X-internal"). Carried inside the JSON ring as object-shaped sentinels. Cross-language receivers that can't reconstruct fail at wire compile.

**`$function_pointer` reconstruction — wrapper binary + persistent subprocess (issue 318, amended 2026-05-22).** Earlier design had the consumer's spec FFI-cast the raw process-local address. Rejected: FFI is language-pair-specific, biases SoraMech toward the Lua↔C corner, breaks the N-not-N² rule. Replacement: at map-compile time the compiler asks the *producing* spec to compile the referenced function + its enumerable dependencies into a standalone wrapper binary on disk that speaks a small line protocol on stdio. The consumer spec spawns one persistent subprocess per `$function_pointer` it receives and talks to it over the same socket-like channel used for any out-of-process spec. Every language pays the same price; new languages only implement "compile a function to a wrapper binary" — no pair-wise FFI knowledge required.

**Spec `invoke` signature change.** Collapses `invoke_native` and `invoke_json` into one `invoke` with per-input/per-output flags: `int invoke(handle, ..., const int *input_native, int n_inputs, int output_native, void *out_buf, ...)`. The spec dispatches per input internally. This is the contract change that unblocks 306/307's typed marshalling.

**Two compile-time layers stack:**
- **Per-edge classification (issue 312, this design)** — graph loader computes `input_edge_native[]` and `output_edge_native[]` on each box; dispatch routes pushes accordingly. This issue is the wire-format design.
- **Same-language source merge (issue 313, research / blocked)** — concatenate every same-language box's source into one translation unit per language. Boxes still run as separate thread-pool tasks; what 313 thins is the spec invocation overhead inside the merged region (direct call into the worker's `lua_State` instead of dlsym + marshal + bridge). The dual-ring slot machinery does NOT collapse — tasks still need slots to wait for sibling inputs. 313 makes the ring cells cheaper to read/write; it doesn't remove them.

**Three rejected design shapes** (kept here so they don't get reinvented):
1. **Handles back-routing to the owning spec** — library functions in the wild can't be modified to use SoraMech-shaped handles. Rejected.
2. **Pair-wise language paths** — every new language would have to grow N-1 translation paths against existing languages. Rejected. The dual-ring's "two rings per slot" is the dimension-cap that prevents this.
3. **Per-function discriminator / length annotations on the wire** — the system has no universal vocabulary to ask "is param 2 the length?" Rejected; the user expresses these by wiring two separate input slots.

**How to apply:** When discussing wire format, slot store shape, dispatch routing, or spec callbacks: think dual-ring (native, JSON, ordering) per slot, per-edge classification at push time, per-cell tag at pop time, JSON-only-at-borders, language-private native bytes everywhere else.

```

### project_custom_translation_specs.md

```markdown
---
name: Custom translation specs per port
description: Users can override the default native/JSON wire path on any input port for any reason — a knob in the wire format vocabulary (issue 246)
type: project
originSessionId: 1228a221-1c09-4c26-94f3-172d7777b2b9
---
**Per-port custom translation specs** let the user intervene at a specific input port and replace the default dual-ring decode path with user-written code. The override applies to that one port; the rest of the graph uses the default native-or-JSON path from issue 312.

**Motivating cases (any reason qualifies, not just cross-language):**
- Cross-language ambiguity the default specs can't infer: a C++ class with methods landing at a C box (drop methods? expose as fn pointers? restructure?), a `void *` carrying a libcurl handle, a union whose discriminator is on a separate wire.
- Same-language reshape: massaging a value into a different shape on its way in (rename fields, drop a layer, project a subset) without adding a transform box on the canvas.
- Validation / coercion: clamp a number, enforce a schema, fail loudly on unexpected shapes.

**How it composes with the dual-ring design:**
- The custom spec runs at *pop* time on the consumer side, after the ordering ring has been consulted and the cell has been read from the appropriate ring. The user's code receives the decoded value (native or JSON-decoded) and produces whatever the consumer's `invoke` will see.
- A port with a custom translation gets its own wire color in the editor (issue 245) — visible signal that this port doesn't use the default path.

**Why:** The default native/JSON contract covers the cases JSON's structure handles cleanly. Everything outside that needs a user escape hatch — *and* the same hatch is useful for purely-local "I want this input shaped differently" cases. One mechanism, many uses.

**How to apply:** When the design needs an override knob on the cross-language path, propose "custom translation spec on the destination port" rather than inventing per-function annotations, type discriminator metadata, or producer-side conversion hints (all three were rejected — see feedback_cross_language_pitfalls). The port is the unit of override; the spec is user code; the rest stays default.
```

### project_threading.md

```markdown
---
name: threading_model
description: SoraMech's threading model — phase 2 synchronous, phase 3 SoraMech-owned C thread pool with per-port slots and language specs
type: project
originSessionId: 579d58b3-7452-44f3-983a-80ff5821082a
---
**Phase 2 (current)**: synchronous executor in `src/004-executor.lua`. Single-threaded, sequential box execution. One driver shell-out per box call. The phase 2 path goes away when phase 3 lands — no fallback, no coroutine intermediate.

**Phase 3 (designed, not yet built)**: C pool runner with a SoraMech-owned thread pool. The 3d-rts pool at `/home/ritz/programming/ai-stuff/games/3d-rts/libs/900-task-pool.h` is the **design reference**, not vendored — SoraMech owns its pool implementation so the spawn primitive, worker context, init barrier, and iterator-pinning extensions are all under our control. The architecture is fully specified across issues 301–313.

Key phase 3 concepts:
- **Per-input-port slots** (not per-task), allocated at graph load and durable for the run. Each slot is a ring buffer (`n_cells` cells of `cell_capacity` bytes). 1-cell slots use peek-not-drain (literals, single-push wires); N-cell slots use pop-and-drain (queued / multi-push wires). No per-slot refcounting — slot lifetime is the whole run.
- **Tasks are ephemeral**: spawned dynamically by the dispatch layer when a box's input set is ready. Tasks carry just `box_id` and a counter snapshot. Box state (counter, input slots, language handle) is durable.
- **Language specs** under `langs/<name>/spec.so`, loaded via `dlopen` at startup. Uniform `lang_spec_t`. No language is privileged.
- **Same-language fast path** (issue 312): wire format defaults to JSON, but two adjacent same-language boxes use the language's native serialization (Lua `lua_dump`, C struct memcpy). Compile-time wire classification picks the path.
- **In-process specs** (Lua, C) via `lua_pcall` / `dlsym`. **Out-of-process specs** (Bash) via Unix domain sockets to a persistent per-worker subprocess.
- **Dispatch layer** (304) is the worker-side action: pop inputs → branch on box mode → invoke spec → push to downstream input slots → end. No blocking, no wait lists; tasks spawn on input arrival and run to completion.
- **Iterator and comparator routing** in the dispatch layer. Comparator runs the function and routes by output value. Iterator skips the function and routes by per-box counter (atomic spawn-time increment). Iterator tasks parallelize across workers; ordering preserved via per-push counter tags on consumer slots.
- **No-null rule** (issue 230): every input port must be wired, given a literal, or marked optional. Compile fails on missing inputs.
- **Init barrier**: pool startup waits until every worker has run every spec's `init(worker_idx)` before submitting tasks. Avoids tasks landing on uninitialized handles.
- **Hard-crash error policy**: nonzero return from any spec aborts the program.
- **Blocking semantics**: long-running operations tie up a worker. Pool size is the budget. Cooperative split (kickoff + check-done iterator) avoids holding a worker. See `docs/004-ipc-and-threading.md`.

**Effil is explicitly NOT used.** Coroutines are not used. The C pool is the chosen mechanism. 3d-rts is referenced as design inspiration, not vendored.

**How to apply:** When discussing threading, parallelism, or cross-language IPC: phase 2 is synchronous shell-out drivers; phase 3 is the SoraMech-owned C pool runner with `lang_spec_t`, per-port slot stores, and dispatch-layer routing. Never suggest effil. 3d-rts is a reference, not a dependency. Issues 301–313 carry the design.
```

- **Per-worker teardown**: free everything the handle owns at pool shutdown.

## B. Source → executable
- **Compile a source file** (optional, NULL if not applicable) into an artifact the spec can later invoke, honoring per-box `cflags` / `link_libs` / `headers` when a `box_t` is passed.
- **Lazy/no-box compile** for ad-hoc references (the C spec's `/tmp/<hash>.so` path).

## C. The three invoke variants (issue 312)
- **`invoke` (canonical)**: per-call entry; reads each input's `input_native[i]` flag and dispatches internally to its native or JSON decoder; writes output in the form requested by `output_native`.
- **`invoke_native` (optional fast path)**: all neighboring wires are same-language; bytes are this spec's native serialisation, no encode/decode round-trip.

## 1. Why `invoke` alongside `invoke_native` / `invoke_json`?

The two fast paths handle the *uniform* cases: every input native, or every input JSON. They don't handle a third case that genuinely exists: **a single call where some inputs are native and others are JSON** (a Lua box reading from one Lua producer and one C producer). That's the case the canonical `invoke` covers, by routing per-input using the `input_native[i]` flag.

You *could* eliminate it — but only by mandating that the dispatch layer always normalise inputs to one form before the call (e.g. "if any input is JSON, convert everything to JSON, call `invoke_json`"). That's a real design choice with a real cost: you'd be doing one needless `native_to_json` per non-matching input on every mixed call.

`★ Insight ─────────────────────────────────────`
- `invoke` isn't really a third *variant* — it's the **general form** that the other two are *specialisations* of. The two fast paths exist because they let the spec skip per-input branching and per-call format checks in the hot loop.
- A simpler contract would be: spec implements only `invoke`, and the dispatch layer hints "all native" or "all JSON" via the flags. The spec internally chooses the cheap path. That trades a few branches for one fewer entry point.
─────────────────────────────────────────────────

**Question back:** is the hot-loop branch cost worth a second entry point to you, or would you rather collapse to one `invoke(flags…)` and let the spec author decide internally?

## 2. Shell-out wrappers — yes, with one wrinkle: persistent subprocesses

You asked for arguments against. I tried to think of real ones, not strawmen:

- **Fork+exec cost is ~1ms per call.** For a tick-driven dataflow loop where cross-language calls happen per tick, that dominates everything. FFI is microseconds. This is the main reason teams reach for FFI even though it's brittle.
- **State doesn't survive across calls.** A function pointer that holds a counter, a loaded model, a cached connection — all gone the moment the subprocess exits. The wrapper sees a fresh binary every call.
- **Argument enumeration is hard in dynamic languages.** Lua closures capture upvalues and `_ENV`. Statically figuring out *all the dependencies* of a function pointer at compile time is the FFI problem in different clothes.

But — and this is the part that resolves it for me — the **threading roadmap already commits to Unix domain sockets for cross-language IPC** (per memory). So the actual implementation isn't "fork+exec per call." It's:

- At map compile time, generate the wrapper *and* spawn the target-language subprocess once. It listens on a Unix socket.
- The wrapper, when called, sends `(fn_name, args)` over the socket and waits for the result.
- State lives in the long-running subprocess. Latency is socket round-trip, ~10–50µs, not fork latency.

That sidesteps the cost concern *and* the state concern in one move. The subprocess becomes the natural home for the function pointer's closure state.

`★ Insight ─────────────────────────────────────`
- The shell-out-binary-with-args framing and the persistent-socket-subprocess framing aren't actually different designs — the first is the simple-case skin of the second. ## Must decide before implementing

### Concern A — Where do decoded native values *live*?

The current `invoke` signature takes `input_data[]` as bytes-and-sizes. But your new design says dispatch decodes JSON to native *before* invoke. So what does invoke receive?

Two coherent answers:

1. **Native lives in the runtime store.** Dispatch calls `json_to_native(handle, json_bytes)` which pushes onto Lua's stack (or C's typed-pointer table, etc.). `invoke` takes only `n_inputs` and pulls from the store directly. The bytes arrays in the current signature go away.
2. **Native is a separate byte form.** Dispatch decodes JSON-bytes → native-bytes (e.g. msgpack for Lua). `invoke` receives those native bytes and decodes them into runtime values itself.

(1) is faster and aligns with the existing bridge convention (Lua's bridge already pushes/pops via stack). (2) keeps the current invoke signature but means every spec maintains *two* serialised forms — a native one and JSON — which is awkward.

I recommend (1). But it means **the invoke signature changes shape** — that's a contract change, not just adding/removing fast paths. Worth being explicit about in the issue.

### Concern B — What does "same-language wire" actually mean?

Two same-language boxes (Lua → Lua) don't share a `lua_State` (each worker has its own; boxes don't generally share state). So the value can't just sit on a stack across the boundary. *Something* has to serialise it.

Two options:

1. **Same-language wires use language-native bytes (msgpack for Lua, struct memcpy for C).** That needs **two more bridge functions per spec**: `native_to_bytes` and `bytes_to_native`. Cheap, agnostic, but adds to the contract.
2. **Same-language wires force producer and consumer onto the same worker, share the stack directly.** Much faster (no serialisation at all) but it constrains the scheduler — you've now coupled wire topology to worker affinity. Once a wire goes cross-language, that constraint disappears, so it's a heterogeneous policy.

If you want the fast path to be genuinely fast, you probably want (2) for same-language and (1) only as the fallback when affinity can't be honoured. But (2) is the bigger commitment — it touches the scheduler, not just the spec contract.

Worth declaring which one you're committing to in 312, or marking the same-language fast path as "deferred decision; route through JSON for now."

## Smaller concerns — flagging, not blocking

- **Bridge contract becomes mandatory, not optional.** Existing specs (Lua, C, Bash) all need bridges before 312 lands or the whole runtime breaks. Worth a migration note.
- **`invoke_native` / `invoke_json` removal touches the existing header comments and `langs/{lua,c,bash}/spec.c` files** — small mechanical sweep, easy to miss.
- **Error semantics shift slightly**: today a malformed JSON input is the spec's problem; under the new flow, `json_to_native` raises at the dispatch layer before invoke ever runs. 114	function / userdata / thread (`langs/lua/spec.c:317`). Sentinels
115	land in a later slice.
116	
117	## Per-edge classification at graph load
118	
119	The graph loader's single-threaded phase walks every connection
120	and computes per-box arrays:
121	
122	- `input_edge_native[i]` — one bit per input port. True iff every
123	  producer feeding that port shares the consumer's language.
124	- `output_edge_native[j]` — one bit per outgoing connection. True
125	  iff the consumer on the other end shares this box's language.
126	
127	Both arrays are already declared and populated — see
128	`src/010-graph-loader.h:145` and `src/010-graph-loader.c:689-754`.
129	
130	Under dual-ring, only `output_edge_native[j]` is consulted on the
131	push path (it picks the ring at write time). The consumer-side bit
132	`input_edge_native[i]` is now informational — the actual per-cell
133	ring tag lives in `ring_order` and is precise per cell.
134	
135	The per-box `use_native_invoke` summary is **removed**. The
136	dispatch reads `ring_order` per pop and consults the cell's tag
137	directly.
138	
139	### Why per-edge, not per-box
140	
141	The earlier per-box approximation collapsed on the first
142	cross-language edge it found — a Lua box with one C neighbor went
143	JSON across all its other edges. Per-edge keeps the cost local to
144	the actual cross-language boundary. The interior of any
145	same-language island skips JSON; only the boundary edges pay. The
146	implementation cost is identical: same number of bits per box,
147	stored per-port / per-connection instead of per-box.
148	
149	Dual-ring takes precision one step further: even on a single port
150	with mixed fan-in, each individual cell is in the right ring. The
151	boundary tightens from "edges that cross languages" to "cells
152	that crossed languages."
153	
154	## Runtime dispatch
155	
156	### Input-read
157	
158	For each input port:
159	```c
160	(which_ring, idx) = ring_order_pop(slot->ring_order)
161	cell_bytes        = ring_at(which_ring == NATIVE ? slot->ring_native
162	                                                  : slot->ring_json,
163	                            idx)
164	input_data[i]   = cell_bytes
165	input_native[i] = (which_ring == NATIVE)
166	```
167	
168	`input_native[i]` is a per-input flag the spec consults to know
169	whether `input_data[i]` is its native form or JSON.
170	
171	### Spec invoke
172	
173	The spec's `invoke` signature gains per-input and per-output flags:
174	
175	```c
176	int invoke(handle, file_path, fn_name,
177	           const void **input_data, const int *input_sizes,
178	           const int *input_native, int n_inputs,
179	           int output_native,
180	           void *out_buf, int out_buf_capacity, int *out_size);
181	```
182	
183	The spec dispatches per input: if `input_native[i]`, decode as
184	native; else decode as JSON. The output is written in whatever
185	form `output_native` indicates — one form, one write. The previously
186	separate `invoke_native` and `invoke_json` callbacks collapse into
187	this single dispatching `invoke`; the per-input dispatch is what
188	the design actually needs.
189	
190	For boxes whose output fans to multiple consumers in different
191	languages, the dispatch picks one form for `output_native` based
192	on whichever ring is dominant (typically native if any
193	same-language consumer exists; the cross-language consumers eat a
194	`native_to_json` conversion at push time). The detail is a runtime
195	optimization, not a correctness concern.
196	
197	### Output-push
198	
199	```c
200	for each outgoing connection j:
201	    if output_edge_native[j]:
202	        push native_bytes      to consumer->ring_native
203	        push (NATIVE, idx)     to consumer->ring_order
204	    else:
205	        if output_was_native: json_bytes = spec->native_to_json(native_bytes)
206	        push json_bytes        to consumer->ring_json
207	        push (JSON, idx)       to consumer->ring_order
208	```
209	
210	If the spec produced native and multiple cross-language consumers
211	exist, the dispatch calls `native_to_json` once and reuses the
212	JSON bytes across every cross-language push (optimization, not
213	required for correctness).
214	
215	## Edge cases
216	
217	- **All-same-language graph**: every connection's
218	  `output_edge_native[j]` is true; `ring_json` stays unallocated
219	  across every slot; activity is on `ring_native` and `ring_order`
220	  only.
221	- **All-different-language graph**: every connection routes to
222	  `ring_json`; `ring_native` stays unallocated.
223	- **Mixed fan-in**: both rings active on the same slot. Consumer
224	  sees a mix of native and JSON cells, picked apart by
225	  `ring_order`.
226	- **Type changes mid-development**: a wire that was Lua→Lua
227	  becomes Lua→C when the user changes a downstream box's language.
228	  The graph loader recomputes the per-edge bits on the next load;
229	  no data conversion at runtime, no migration.
230	
231	## Implementation cost
232	
233	- **Slot store**: two rings per slot instead of one, plus the
234	  ordering ring. Allocate `ring_json` and `ring_order` lazily —
235	  same-language-only slots pay nothing for them. Per-cell cost:
236	  one extra ordering-ring write on push, one extra read on pop.
237	- **Spec interface**: one signature change to the `invoke`
238	  callback adding `input_native[]` and `output_native`. Every
239	  spec's `invoke` gains a per-input branch. Lua's branch is
240	  almost free — both decoders (`json_to_native` and the future
241	  native one) already exist as bridges. C and Bash need their
242	  JSON bridges written, which is shared with the broader
243	  cross-language work in 307/308.
244	- **Dispatch**: one extra step on read (consult ordering ring),
245	  one extra branch on push (which ring to write).
246	
247	The win is exactness: same-language values stay native even when
248	their port has a cross-language sibling producer.

250	## Future: whole-program same-language compilation (issue 313)
251	
252	313 describes merging all same-language source into one
253	translation unit per language at compile time. The merge does
254	**not** eliminate the slot store for same-language wires — boxes
255	still run as separate tasks in the thread pool, possibly on
256	different workers, so values still need a place to wait for
257	sibling inputs to arrive. The thread pool's parallelism depends
258	on tasks being scheduled independently; collapsing same-language
259	hops to direct function calls would serialize execution and defeat
260	the pool.
261	
262	What 313 thins is the **spec invocation overhead**: for boxes in
263	the merged region, the dispatch can call the function directly on
264	the worker's `lua_State` (or compiled C code) without going
265	through dlsym + bytes-marshal + bridge. The dual-ring slot shape
266	remains; 313 makes the native-ring's read/write cheaper. The two
267	layers stack, they don't cancel.

269	## Resolved design choice: JSON, not type-annotated raw bytes
270	
271	An earlier note asked whether cross-language wires should use
272	type-annotated raw byte encodings (length-prefixed ints, raw
273	floats, etc.) instead of JSON. **Decided: JSON across the board
274	for the cross-language ring.** Rationale:

6	## Concept
7	
8	JSON's structure covers six kinds of value cleanly — object,
9	array, number, string, bool, null — and the cross-language ring
10	in the dual-ring slot (issue 312) carries JSON for any wire that
11	crosses a language boundary. The structural cases that don't fit
12	those six kinds — Lua closures, libcurl handles, C++ class
13	instances, file handles, function pointers, large byte buffers
14	where serialization would be expensive — need somewhere to live
15	in the JSON ring without forcing the wire format to grow new
16	top-level shapes.
17	
18	**Sentinel primitives** are JSON object shapes with reserved key
19	names that mean "this isn't a structural value, it's a reference
20	to something the consumer must reconstruct using language-specific
21	machinery."
22	
23	Three kinds, each solving a different structural gap:
24	
25	```json
26	{"$ref":              {"ptr": "0x...",  "len": 1048576,
27	                       "type": "bytes"}}
28	{"$function_pointer": {"addr": "0x...", "signature": "int(void*,void*)"}}
29	{"$lang_opaque":      {"lang": "lua",   "tag": 12345,
30	                       "shape": "coroutine"}}
31	```
32	
33	Sentinels are **emitted by the producer's spec** when its language
34	has a value JSON can't represent structurally. They are
35	**reconstructed by the consumer's spec** using whatever runtime
36	machinery that language provides (LuaJIT FFI, ctypes for Python,
37	direct cast for C, etc.). Wires whose consumer cannot reconstruct
38	a sentinel kind **fail at compile time** — the editor catches the
39	mismatch when the user wires a function-pointer output into a
40	Bash input.
41	
42	## Why these three, not more
43	
44	The three sentinels carve up the structural gap by ownership:
45	
46	- **`$ref`** — bytes in a shared heap. The producer wrote the
47	  bytes to the large-value heap (issue 302 / `src/015-large-value-heap.c`)
48	  and emits a pointer-and-length reference. The bytes are
49	  immutable for the wire's lifetime; refcount tracks consumers.
50	  Solves: "I have a megabyte to share; copying it through the
51	  slot would be wasteful."
52	- **`$function_pointer`** — a callable, identified by a raw
53	  address and a signature interpretable in C-function-pointer
54	  syntax. The address is process-local. The signature is the
55	  contract between producer and consumer. Solves: "I have a
56	  function I want my consumer to be able to call directly."
57	- **`$lang_opaque`** — a language-private value. The producer
58	  tags it with the language name and a worker-private reference
59	  the producer's spec can resolve back. Solves: "I have a value
60	  with no general structural representation; only my own
61	  language knows what it is."

64	JSON-structural representation and shouldn't be a sentinel, or
65	(b) is genuinely unrepresentable and the wire is wrong, not the
66	format.

95	
96	The C spec's generated wrapper (issue 307) knows the box's
97	declared output type. The wrapper emits the right sentinel
98	shape based on the type:
99	
100	- A declared `function_pointer` return — `$function_pointer`
101	  with the type's signature.
102	- A declared `bytes` return whose size exceeds the inline
103	  threshold — `$ref` with the bytes written to the heap.
104	- A declared opaque struct — `$lang_opaque` if the struct's
105	  shape is C-only.
106	
107	### Bash
108	
109	Bash has no native values besides strings; sentinels don't apply
110	on the emit side. A Bash producer always emits structural JSON
111	strings.
112	
113	## Consumer protocol
114	
115	Each spec's `json_to_native` walks the JSON tree and, when it
116	sees a sentinel key, reconstructs the value using its language's
117	machinery. The reconstruction is the spec author's responsibility.
118	
119	### Lua
120	
121	```c
122	// inside lua_json_to_native, on seeing {"$function_pointer": {...}}:
123	const char *sig = json_string_value(obj, "signature");
124	uintptr_t   addr = json_int_value(obj, "addr");
125	lua_getglobal(L, "ffi");
126	lua_getfield(L, -1, "cast");
127	lua_pushstring(L, sig);                 // "int (*)(void*, void*)"
128	lua_pushinteger(L, (lua_Integer)addr);
129	lua_call(L, 2, 1);
130	// stack top: an FFI callable Lua can invoke as compare_fn(a, b)
131	```
132	
133	`$ref` reconstruction in Lua copies the bytes (`lua_pushlstring(ptr, len)`)
134	since Lua's value model needs values in Lua's heap. The
135	producer's refcount handles the lifetime.
136	
137	`$lang_opaque` with `lang: "lua"` resolves the tag through the
138	worker's per-worker registry; with `lang != "lua"` it's a wire
139	compile error.
140	
141	### C
142	
143	Direct casts. `$function_pointer` becomes a typed function
144	pointer the wrapper can invoke. `$ref` is a `(void*, size_t)`
145	pair the wrapper hands to the user's function. `$lang_opaque`
146	with `lang: "c"` is a typed-struct pointer; other langs fail.
147	
148	### Bash
149	
150	Bash cannot reconstruct any sentinel except possibly `$ref`
151	(by reading the bytes from the file the marshaller staged at the
152	process boundary). `$function_pointer` and `$lang_opaque` fail
153	unless the producer chose the cross-process escape hatch (see
154	below).
155	
156	## Compile-time validation
157	
158	The compile step walks every wire and checks:
159	
160	- If the producer's declared output type can emit sentinel kind
161	  K (per the producer language's spec capability), then
162	- The consumer's language must be able to reconstruct sentinel
163	  kind K (per the consumer language's spec capability).
164	- If not, **the compile fails** with the specific wire and the
165	  specific sentinel kind named.
166	
167	This is editor-time feedback. The user fixes the wire
168	(reroute it, change the consumer's language, attach a custom
169	translation per issue 246) before the program ever runs.
170	
171	The per-spec capability is a static fact each spec declares.
172	Adding a new language K declares K's emit set and reconstruct
173	set; the compile validator consults the declaration.
174	
175	## Cross-process escape hatch for `$function_pointer`
176	
177	Bash (and any other process-isolated language) can't dereference
178	an in-process function-pointer address. Two options when a
179	function pointer's wire targets such a consumer:
180	
181	1. **Fail at compile time** (the default). Clear, honest.
182	2. **Producer-side compiled binary** (opt-in). When the C spec
183	   detects that a function-pointer output is wired to a
184	   cross-process consumer, it compiles the function into a
185	   standalone executable in `compiled/cross-process/<box>__<port>.bin`.
186	   The sentinel becomes:
187	
188	   ```json
189	   {"$function_pointer": {"binary": "compiled/cross-process/...",
190	                          "signature": "int(int,int)"}}
191	   ```
192	
193	   Bash invokes the binary with `$(./bin args...)` per call. Cost:
194	   process spawn per invocation (1-10 ms). The escape hatch is
195	   opt-in per box output — the user explicitly chooses the cost
196	   in the inspector.
197	
198	The default behaviour is option 1 because hiding the spawn cost
199	would mislead the user about runtime behaviour. The user picks
200	their language; the cost follows from the choice. Option 2 is
201	the escape hatch for cases where the user genuinely needs
202	C-from-Bash and accepts the cost.
203	
204	## Relationship to custom translation specs (issue 246)
205	
206	Sentinels are the **spec author's tool** for representing
207	non-structural values. Custom translations are the **user's
208	tool** for interpreting them (or any other value) when the
209	default reconstruction isn't what they want.
210	
211	The escalation path:
212	
213	1. Default spec encode / decode handles JSON-structural values
214	   transparently.
215	2. When the producer's value can't be encoded structurally, the
216	   spec author's emit logic produces the right sentinel.
217	3. When the consumer's spec can reconstruct the sentinel
218	   generically (FFI cast, ctypes, direct pointer), the default
219	   reconstruction runs.
220	4. When the user wants a different interpretation than the
221	   default (treat a function pointer as a method on a class
222	   instance, dereference a `$ref` and parse its bytes as a
223	   custom format, etc.), they attach a per-port custom
224	   translation that overrides the default reconstruction.
225	
226	So sentinels and custom translations are layered: sentinels
227	provide the *bytes that arrive at the wire* for non-structural
228	values; custom translations decide *what to do with those bytes*
229	when the default isn't enough.
230	
231	## Where in the dispatch this lives
232	
233	Sentinels live inside the JSON ring of the dual-ring slot. The
234	slot store (issue 312) doesn't know about them — it just carries
235	bytes. The producer's `native_to_json` emits them when writing
236	to the JSON ring; the consumer's `json_to_native` recognizes
237	and reconstructs them when reading from the JSON ring.
238	
239	Inside the native ring, sentinels don't appear — native values
240	are encoded in the language's own binary form, which can
241	represent its own callables / opaque values directly without
242	needing a JSON-side hack.
243	
244	## Relevant files

267	## Suggested implementation sequence
268

270	   exact key names, value-object schemas. Document in

272	2. **Lua emit**: replace the hard-errors in `encode_value` with

278	4. **Per-spec capability declarations**. Each spec declares its
279	   emit set (sentinel kinds it can produce) and reconstruct set
280	   (sentinel kinds it can consume). Lives next to the
281	   `lang_spec_t` declaration.
282	5. **C spec sentinels**. Emit via the generated wrapper based on
283	   declared output types; reconstruct via direct cast.
284	6. **Bash spec sentinels**. Only `$ref` on the reconstruct side
285	   (read bytes from the marshaller's staged file).
286	7. **Compile-time validation**. Walk every wire; check the
287	   producer's emit set against the consumer's reconstruct set;
288	   fail with a clear message on mismatch.
289	8. **Cross-process escape hatch for `$function_pointer`**.
290	   Opt-in flag in the box output declaration; the C spec emits a
291	   standalone binary instead of (or alongside) the in-process
292	   address.
293	
294	## Open questions
295	
296	- **`$ref` lifetime across iterator-fed slots**. A producer's
297	  output is referenced by an N-cell ring of consumer slots; each
298	  cell holds the `$ref`, each pop decrements. Already supported
299	  by the large-value heap's refcount, but worth verifying the
300	  test coverage when sentinels land.
301	- **Sentinel inside sentinel.** A `$ref` whose bytes are
302	  themselves JSON containing a `$function_pointer` is legal but
303	  weird. Document the recursive case; probably falls out of the
304	  walker for free.
305	- **Versioning the sentinel format**. The reserved key names
306	  (`$ref`, `$function_pointer`, `$lang_opaque`) and the
307	  value-object schemas are part of the compile-time contract.
308	  Changing them is breaking. Worth a one-line stability note
309	  somewhere.
310	- **Cross-process `$ref` semantics**. In-process `$ref` is a raw
311	  pointer + length. Cross-process (Bash via UDS), the marshaller
312	  stages the bytes at the socket boundary. Decide whether the
313	  Bash-side `$ref` reconstruction reads from a file path or
314	  inlines the bytes in the request. The latter is simpler; the
315	  former scales to bigger values.
316	- **`bytes` returns on the C spec currently passthrough raw bytes
317	  into the JSON ring.** The C spec's typed-output-JSON path
318	  (issue 307 item 2) wraps strings in JSON quotes and passes
319	  ints / doubles / bools through as valid JSON fragments — but for
320	  a declared `bytes` return it writes the raw payload verbatim,
321	  which is *not* valid JSON in the general case (non-UTF-8 bytes
322	  break parsers; embedded quotes / backslashes mangle the wire).
323	  The proper resolution belongs here, not in 307: small `bytes`
324	  outputs should be base64-wrapped into a JSON string (or its own
325	  sentinel kind), and large `bytes` outputs should follow the
326	  `$ref` path already described for the heap. Until that lands,
327	  cross-language `bytes` wires from C producers are an honest
328	  hazard — flag in the compile-time validator if possible, or at
329	  minimum document the gap so users don't wire a `bytes`
330	  C-output into a Lua / Bash consumer expecting clean JSON.

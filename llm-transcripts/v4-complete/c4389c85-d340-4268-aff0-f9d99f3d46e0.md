## 1. Undo the existing system-wide install (on each host)

The official install script put things in `/usr/local`. Remove those first:

```bash
sudo systemctl stop ollama 2>/dev/null
sudo systemctl disable ollama 2>/dev/null

sudo rm -f /usr/local/bin/ollama
sudo rm -rf /usr/local/lib/ollama
```

If the script created an `ollama` user/group, you can leave them or `sudo userdel ollama && sudo groupdel ollama`.

## 2. Install manually to `/home/sora/programs/ollama/`

Don't re-run `install.sh` — it's hard-wired for `/usr/local`. Extract the tarball yourself:

```bash
mkdir -p /home/sora/programs/ollama
cd /home/sora/programs/ollama
curl -L https://ollama.com/download/ollama-linux-amd64.tgz -o ollama.tgz
tar -xzf ollama.tgz
rm ollama.tgz
```

You'll end up with `/home/sora/programs/ollama/bin/ollama` and `/home/sora/programs/ollama/lib/ollama/`.

Quick sanity check:

```bash
/home/sora/programs/ollama/bin/ollama --version
```

## 3. Write a launcher script (per host, with the right IP)

Save this as `/home/sora/programs/ollama/serve.sh`. **Set `BIND_IP` to `192.168.1.11`, `.12`, or `.13` depending on the host:**

```bash
#!/bin/bash
DIR="/home/sora/programs/ollama"
BIND_IP="192.168.1.11"   # change to .12 on host 2, .13 on host 3
PORT="10000"

export OLLAMA_HOST="${BIND_IP}:${PORT}"
export OLLAMA_MODELS="${DIR}/models"
export PATH="${DIR}/bin:${PATH}"

mkdir -p "${OLLAMA_MODELS}"
exec "${DIR}/bin/ollama" serve
```

Make it executable: `chmod +x /home/sora/programs/ollama/serve.sh`

## 4. Run it as a systemd service (recommended)

Create `/etc/systemd/system/ollama.service`:

```ini
[Unit]
Description=Ollama (sora)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=sora
Group=sora
ExecStart=/home/sora/programs/ollama/serve.sh
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
```

Then:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now ollama
sudo systemctl status ollama
```

If you don't want systemd, just run `nohup /home/sora/programs/ollama/serve.sh > /tmp/ollama.log 2>&1 &`.

## 5. Verify from another machine

From any of the three hosts (or your dev box):

```bash
curl http://192.168.1.11:10000/api/tags
curl http://192.168.1.12:10000/api/tags
curl http://192.168.1.13:10000/api/tags
```

Each should return JSON (likely `{"models":[]}` until you pull one).

Yes — Alpine has three differences that bite here:

## 1. Ollama is built against glibc; Alpine uses musl

The `ollama-linux-amd64.tgz` you downloaded is a glibc binary. It will fail to start on Alpine with something like `not found` (which is actually the dynamic linker complaining, not the file missing). Install the glibc shim:

```bash
apk add gcompat libstdc++ libgcc curl
```

`gcompat` provides a glibc-compatible loader; the other two cover the C++ runtime Ollama links against. Test after installing:

```bash
/home/sora/programs/ollama/bin/ollama --version
```

If it prints a version, you're good. If you still get loader errors, the heavier alternative is `apk add --no-cache build-base go cmake git` and build Ollama from source — but try `gcompat` first, it usually just works.

> Aside: that "API is now available at 127.0.0.1:11434" message from the official `install.sh` is printed unconditionally — it doesn't mean the daemon actually started under Alpine. Don't trust it.

## 2. Alpine uses OpenRC, not systemd

Replace my systemd unit with an OpenRC init script. Save as `/etc/init.d/ollama`:

```sh
#!/sbin/openrc-run

name="ollama"
description="Ollama LLM server"

command="/home/sora/programs/ollama/serve.sh"
command_user="sora:sora"
command_background=true
pidfile="/run/ollama.pid"
output_log="/var/log/ollama.log"
error_log="/var/log/ollama.log"

depend() {
    need net
    after firewall
}
```

Then:

```bash
chmod +x /etc/init.d/ollama
rc-update add ollama default
rc-service ollama start
rc-service ollama status
```

Logs land in `/var/log/ollama.log` instead of `journalctl`.

## 3. Firewall — no `ufw` on Alpine

Alpine ships with no firewall enabled by default. If you've set one up, it's most likely `awall` over nftables. Two cases:

**No firewall configured:** nothing to do, port 10000 is already open.

**awall in use:** add a policy in `/etc/awall/optional/ollama.json`:

```json
{
  "filter": [
    { "in": "internet", "out": "_fw", "service": "ollama", "action": "accept" }
  ],
  "service": {
    "ollama": [ { "proto": "tcp", "port": 10000 } ]
  }
}
```

Then `awall enable ollama && awall activate`.

**Raw nftables:** `nft add rule inet filter input tcp dport 10000 accept` and persist via `/etc/nftables.nft`.

## 4. Minor: user creation if `sora` doesn't exist yet

Alpine's `adduser` is the busybox variant:

```bash
adduser -D -h /home/sora -s /bin/sh sora
```

`-D` skips password prompt. Add to a group with `addgroup sora <group>`.

The tarball extraction, the `serve.sh` launcher, the `OLLAMA_HOST` / `OLLAMA_MODELS` env vars, the per-host IP table, the `curl /api/tags` verification — all unchanged.

Not hard. Ollama is Go + a vendored llama.cpp (C++), and both build cleanly on Alpine/musl. Expect 10–30 min per host depending on CPU — or build once and `scp` the binary to the other two, since the arch matches.

## Build-time dependencies

```bash
apk add --no-cache build-base cmake git go bash
```

- `build-base` pulls in `gcc`, `g++`, `make`, headers — needed for the llama.cpp half.
- `cmake` because llama.cpp's build is CMake-driven.
- `go` from Alpine's repos is already musl-linked, which is exactly what you want.
- `bash` because Ollama's build scripts use bash, not POSIX sh.

## Runtime dependencies

After the build, on each host that runs the binary:

```bash
apk add --no-cache libstdc++ libgcc
```

That's it. No `gcompat`. Go binaries are mostly self-contained; the only dynamic links left are the C++ runtime bits from the vendored llama.cpp via cgo.

## Build it

```bash
cd /home/sora/programs
git clone https://github.com/ollama/ollama.git ollama-src
cd ollama-src
git tag | tail -20            # pick a recent stable tag, avoid building HEAD
git checkout v0.x.y           # whatever you picked
make -j$(nproc)
```

When that finishes you'll have `./ollama` in the repo root. Move it into place:

```bash
mkdir -p /home/sora/programs/ollama/bin
cp /home/sora/programs/ollama-src/ollama /home/sora/programs/ollama/bin/ollama
chown -R sora:sora /home/sora/programs/ollama
```

Verify musl, no gcompat:

```bash
ldd /home/sora/programs/ollama/bin/ollama
```

You should see `ld-musl-x86_64.so.1`, `libstdc++.so.6`, `libgcc_s.so.1`, `libc.musl-x86_64.so.1`, and that's about it. If `gcompat`'s loader shows up, something pulled it in — uninstall `gcompat` and rebuild.

Quick sanity check:


If you want zero runtime deps (no `libstdc++`/`libgcc` install), you can try a fully static build by linking C++ statically. It's doable but fragile — llama.cpp's CMake doesn't expose a clean switch for it, you'd be patching `CGO_LDFLAGS` and hoping nothing breaks. Not worth it for three trusted hosts. The dynamic-link approach is the right trade-off here.

---

One question back at you, since this is the kind of thing that's easy to get wrong once and live with forever: **do you want all three hosts to be independently capable of rebuilding (so any one can be your "golden" host), or do you want one designated build host and the other two as binary-only runtime nodes?** The first costs ~150MB extra per host (Go toolchain + build-base) but means no special-casing; the second is leaner but adds an implicit dependency ("which host do I update from?"). For three hosts I'd lean toward the first — symmetry beats minimalism at this scale — but it's a design taste call.

## 1. The missing `go` package

Alpine's `apk search` only matches the start of the name by default, and only against your enabled+updated index. What I'd check first:

```bash
apk update
apk search '^go$'
```

If `go` still doesn't show up, your `community` repo line probably points at an Alpine version that doesn't carry it (older or `edge`-only). Check `/etc/apk/repositories`:

```bash
cat /etc/apk/repositories
```

You want a line like `https://dl-cdn.alpinelinux.org/alpine/v3.21/community` (or whatever Alpine version matches `/etc/alpine-release`). If only `main` is enabled, add the matching `community` line, then `apk update` again.

`gcc-go` (which you found) is GCC's gccgo frontend — it usually lags upstream Go by a major version and has known issues with newer Go features Ollama uses. Don't substitute it.

If community is enabled, indexed, and `go` is genuinely absent in your Alpine version, the only musl-pure fallback is bootstrapping Go from source (slow, ~30 min). I won't bake that into the script — fix the package availability first.

## 2. Always-static build

Two flag groups matter:

- **C++ runtime static**: `-static-libstdc++ -static-libgcc` via `CGO_LDFLAGS`. The C++ pulled in by llama.cpp's cgo bindings is the part that defaults to dynamic.
- **Final link static**: `-linkmode external -extldflags '-static'` in Go ldflags. This forces musl itself to be statically linked too.

The result should pass `ldd ./ollama` with `not a dynamic executable`. If it doesn't, that's a real build problem, not a cosmetic one — and the script bails out.

## 3. The script

Save as `/home/sora/programs/ollama/build-and-deploy.sh` on the build host. Config at the top, peer IPs configurable. Skips the rebuild if the version on disk already matches GitHub's latest release.

```bash
#!/bin/bash
# ollama-build-and-deploy.sh
#
# Build a fully static, musl-linked ollama binary on Alpine, then ship the
# source tree and the compiled binary to two peer hosts. If the most recent
# upstream release tag already matches the version we have on disk, the build
# step is skipped — but the deploy step still runs (idempotent at the peer).
#
# Why this shape: we want one build host doing the heavy lifting, and the
# peers receiving both the binary AND the source so any of them can rebuild
# without depending on this script being re-run. Hardware is identical across
# the three hosts, so the binary is portable.

set -euo pipefail

# {{{ config — override DIR via $1 if you want a different install root
DIR="${1:-/home/sora/programs/ollama}"

PEER_1="192.168.1.12"
PEER_2="192.168.1.13"
PEER_USER="sora"

SRC_DIR="${DIR}/src"
BIN_DIR="${DIR}/bin"
DIST_DIR="${DIR}/dist"
LOG_DIR="${DIR}/tmp"

VERSION_FILE="${DIR}/.built-version"
OLLAMA_REPO="https://github.com/ollama/ollama.git"
GITHUB_API="https://api.github.com/repos/ollama/ollama/releases/latest"
# }}}

# {{{ setup_dirs()
# Create the on-disk layout. The log directory is symlinked into /tmp so build
# noise stays in RAM rather than wearing the disk.
setup_dirs() {
    mkdir -p "${DIR}"
    mkdir -p "${BIN_DIR}"
    mkdir -p "${DIST_DIR}"
    if [ ! -L "${LOG_DIR}" ]; then
        local ram_log="/tmp/ollama-build-$(id -u)"
        mkdir -p "${ram_log}"
        ln -snf "${ram_log}" "${LOG_DIR}"
    fi
}
# }}}

# {{{ ensure_build_deps()
# build-base = gcc+g+++make; cmake for llama.cpp; git+bash+curl for plumbing.
# go must already be installed via apk — if it isn't, we stop here so the user
# can fix the community-repo situation rather than have the script silently
# fall back to a glibc Go shim.
ensure_build_deps() {
    apk add --no-cache build-base cmake git bash curl
    if ! command -v go >/dev/null 2>&1; then
        echo "ERROR: 'go' is not installed." >&2
        echo "Try: apk update && apk add go" >&2
        echo "If apk doesn't find it, enable the community repo for your" >&2
        echo "Alpine version in /etc/apk/repositories and apk update." >&2
        exit 1
    fi
}
# }}}

# {{{ get_latest_tag()
# Ask GitHub for the most recent published release tag. We don't trust git
# ls-remote here because it would include pre-release and draft tags.
get_latest_tag() {
    local response
    response="$(curl -fsSL "${GITHUB_API}")"
    local tag
    tag="$(echo "${response}" | sed -n 's/.*"tag_name": *"\([^"]*\)".*/\1/p' | head -n1)"
    if [ -z "${tag}" ]; then
        echo "ERROR: could not parse latest tag from GitHub API" >&2
        exit 1
    fi
    echo "${tag}"
}
# }}}

# {{{ already_built()
# True if .built-version matches the desired tag AND the binary still exists.
# Either condition failing forces a rebuild — we don't want a stale tag file
# to mask a missing binary.
already_built() {
    local target_tag="$1"
    if [ ! -f "${VERSION_FILE}" ]; then
        return 1
    fi
    if [ ! -x "${BIN_DIR}/ollama" ]; then
        return 1
    fi
    local built_tag
    built_tag="$(cat "${VERSION_FILE}")"
    [ "${built_tag}" = "${target_tag}" ]
}
# }}}

# {{{ fetch_source()
# Shallow clone at the exact tag. Previous checkout is wiped so we never carry
# half-built artifacts from a prior failed run into a new attempt.
fetch_source() {
    local tag="$1"
    rm -rf "${SRC_DIR}"
    git clone --depth=1 --branch "${tag}" "${OLLAMA_REPO}" "${SRC_DIR}"
}
# }}}

# {{{ build_static()
# Two-step build:
#   1. `make` invokes CMake for llama.cpp (produces static .a archives) and
#      then go build for the ollama binary. We pre-set CGO_LDFLAGS so the C++
#      runtime gets pulled in statically.
#   2. We rebuild the Go binary explicitly with -linkmode external and
#      -extldflags '-static', because the upstream Makefile's go invocation
#      doesn't pass those through.
# Final `ldd` check is non-negotiable: if it isn't fully static, we bail loudly
# rather than ship a binary that needs runtime libs the peers might lack.
build_static() {
    cd "${SRC_DIR}"

    export CGO_ENABLED=1
    export CC=gcc
    export CXX=g++
    export CGO_CFLAGS="-O2"
    export CGO_CXXFLAGS="-O2"
    export CGO_LDFLAGS="-static-libstdc++ -static-libgcc"

    local build_log="${LOG_DIR}/build.log"
    make -j"$(nproc)" >"${build_log}" 2>&1

    go build \
        -tags 'netgo osusergo' \
        -ldflags '-linkmode external -extldflags "-static"' \
        -o "${BIN_DIR}/ollama" \
        .

    local ldd_out
    ldd_out="$(ldd "${BIN_DIR}/ollama" 2>&1 || true)"
    if echo "${ldd_out}" | grep -q 'not a dynamic'; then
        echo "OK: binary is fully static."
    else
        echo "ERROR: binary still has dynamic dependencies:" >&2
        echo "${ldd_out}" >&2
        exit 1
    fi
}
# }}}

# {{{ package_dist()
# Bundle the source tree AND the compiled binary into one tarball, so peers
# receive everything needed to either run as-is or rebuild from source.
package_dist() {
```

## ash vs bash, briefly

`ash` (in Alpine, it's busybox's ash) is the small POSIX-focused shell. bash is GNU's larger one with a lot of extensions. The differences that matter for a script like ours:

| feature | bash | busybox ash |
|---|---|---|
| `[[ ... ]]` test | yes | no — use `[ ... ]` |
| arrays | yes | no |
| `<(cmd)` process substitution | yes | no |
| `<<<` herestring | yes | no |
| `{a,b,c}` brace expansion | yes | no |
| `local` in functions | yes | yes (extension) |
| `set -o pipefail` | yes | yes (since busybox 1.30) |
| `$(...)` command substitution | yes | yes |
| `${var:-default}` parameter expansion | yes | yes |
| heredocs | yes | yes |
| `function name() {` | yes | no — use `name() {` |
| `echo -e` | yes (sort of) | yes |

We only use the things in the "both support" rows. Specifically:
- `local var=...` inside functions
- `$(command)` substitution
- `${var:-default}` expansion
- `[ ... ]` tests (POSIX-style, never `[[`)
- `name() { ... }` function syntax (never `function`)
- `set -euo pipefail` (busybox ash supports `pipefail`)
- subshells via `( ... )`
- `for` and `if` (POSIX forms)
- heredocs inside the SSH deploy step

All of that runs under `/bin/sh` on Alpine without modification.

Three branches now:

1. **`serve.sh` per host** — write the launcher with the right `BIND_IP` for each host. No root needed (lives in `/home/sora/programs/ollama/`).

3. **`rc-update add ollama default`** — enable on boot. Needs root.
4. **`rc-service ollama restart`** — restart after a binary update. Needs root.

The script already runs as root locally, so on the build host all four are trivial. The constraint is on **peers**: the deploy step ssh's in as `sora`, who can't write `/etc/init.d/` or invoke `rc-service`. So the question reduces to: how do we get privileged operations on each peer?

Three ways, in order of recommendation:

**1. doas with a narrow rule (recommended).** One-time config on each peer:

```
echo "permit nopass sora as root cmd /sbin/rc-service" >> /etc/doas.d/doas.conf
echo "permit nopass sora as root cmd /sbin/rc-update" >> /etc/doas.d/doas.conf
echo "permit nopass sora as root cmd /bin/mv args /tmp/ollama-init /etc/init.d/ollama" >> /etc/doas.d/doas.conf
```

Then the script ssh's as `sora` and prefixes the privileged calls with `doas`. Tight scope, no full-root ssh.

**2. SSH as root.** Add `PEER_USER_ROOT="root"` config var, ssh-copy-id once to `root@peer1`/`peer2`. Simpler but gives a key full-root access to each peer forever.

**3. Drop a `finalize.sh` on each peer, run it once manually as root.** Service setup happens one time; subsequent binary updates after re-builds wouldn't auto-restart (you'd `rc-service ollama restart` by hand or accept that systemd-style auto-restart isn't happening).

Now both paths use explicit `chmod 755` so the result is the same regardless of umask.

## A roadmap to v1.0


**There is no definition of v1.0 anywhere in the project.** I grepped the
documents, the notes, and the tickets; the roadmap document deliberately
contains no schedule and the phases are described as clusters of functionality
rather than milestones. So the definition below is mine, proposed, and you
should push back on it.


**Proposed: v1.0 is the point where somebody who is not you can build a working
program with this and never have to ask you a question.** That makes the engine
already done and puts every remaining piece of work in the same category — the
approach to the thing, rather than the thing.


By that definition, in order of most value first:


**1. Refill the front door — the steerable panels.** One live control panel
per phase, three regions, levers the reader moves, and a log of what the engine
did about it. This is the single biggest gap between what the project *is* and
what a visitor *sees*, and it is the only remaining item that shows off the
three capabilities that make this engine unusual: writing a value from outside
is an event, the shape can be edited while it runs, and code can arrive after
the program started. Every one of those has no subject until somebody outside
the program acts, which is exactly why the old paged demos deserved deleting.


**2. Get the map writer into the workbench, then finish the round trip.** Build
the parser and writer to WebAssembly with zig, then take steps four through
seven together — validate as you draw, type constants into ports, download the
map plus its layout companion, read one back in. Finishing these makes the
canvas the thing the readme claims it will be: draw a picture, leave with a file
that runs. Right now it is a drawing toy. The wasm step is the keystone and it
just became cheap.


**3. Finish the documentation site.** The two missing interactive pieces, the
mid-page links, and the artistic pass. The steppable termination race is the one
that earns its keep most — that mechanism is genuinely hard to hold in your
head and trivial to see once animated.


**4. Put the transcripts on the site as a book.** Delete one exclusion from the
generator's file-finding command, then page them, fold the machine-generated
blocks, and cross-link them against the issues. This is the smallest remaining
piece and the one your own conventions lean on hardest — the transcripts are
where the arguments survive, and nothing currently reaches them.


**5. The slideshow.** Live-drawn screens, one argument rather than a table of
contents, sharing the simulator built in step two rather than a second one. This
is the most expensive item on the list and the last thing a v1.0 needs, because
it serves a reader who has not decided to care yet.


Below the line, and I'd argue explicitly out of v1.0: **the trail and the
viewer.** Watching a running program from another process is a genuinely good
feature and it is the only remaining item that requires touching the engine —
a ring in shared memory, a build flag, and a rule that a slow reader loses
events rather than holding the program up. Everything above it is about making
the finished engine reachable. Adding a feature to the engine in the same
release you are trying to make the engine approachable is how the
approachability slips.


**Also worth folding into whichever release: the renumbering.** Not because
anything breaks, but because "filenames read in one order across the whole
project" is a claim the readme makes, and four places currently break it.

## The command line as a graph


Your instinct is right and one detail is backwards, and the backwards detail is
the good news.


**A constant parked on a port never participates in the decision to run.** The
engine's numbered promises say it outright: a constant is always present and
never consumed, so it cannot gate anything, and a station made only of constants
is always ready. So if you build the entry station with *the text so far* as a
constant on port zero and *the enter keypress* as an ordinary buffered port on
port one, then:


- Typing a character rewrites the constant. Rewriting a constant is an event —
  it runs the same readiness check any delivery runs — but port one is empty,
  and the engine will not invent a value for an empty port, so nothing runs.
  Typing is silent by construction.

- Pressing enter puts a token in port one. Now every port holds something, so
  the station runs, and it runs with whatever the constant holds at that
  instant.


So the case you worried about — enter with an empty buffer — doesn't fail to
fire, it fires with an empty line. You'd have to *add* something to suppress
that, which is one comparator on the length if you want it.


**Draining is a wire, not a new feature.** A wire whose destination is a
constant port overwrites rather than queues. So the submit station's exit goes
two places: onward to whatever consumes the line, and into a box that takes a
line and returns an empty one, whose exit is wired back into the buffer's
constant port. The clearing is drawn in the picture rather than hidden in a box,
which is the whole reason that rule exists.


**Accumulating is the same shape one step earlier.** An append station: port
zero is the constant holding the line so far, port one is a buffered port
receiving the new character. Its exit wires back into its own port zero. A
constant belongs to exactly one port, so if the submit station also needs to see
the line, that's a second wire to a second constant port rather than a shared
value — visible in the picture, again.


That's the whole terminal, in existing machinery: two entrances, three stations,
four wires, and no engine change.


**And there's a race in it that I want your call on.** The append station does
read-modify-write: peek the line, add a character, write the line back. If two
characters are ever sitting in port one at once, two invocations run
concurrently, both peek the *same* line, both write back, and one keystroke
disappears. The engine already says something in this family out loud — two
arrows into one constant port is last-writer-wins, nondeterministically — so
this is a known shape rather than a surprise, but the terminal walks straight
into it.


Three ways out, best first:


1. **The keyboard reader waits for the graph to fall quiet between characters.**
   The engine already reports when a program has run out of work, and asking to
   be told when it already happened answers immediately, so this is one existing
   call per keystroke. At human typing speed the cost is invisible, and the
   accumulation becomes correct by construction rather than by luck.

2. **Keep the line in the reader thread and write the whole line in on each
   keypress.** No read-modify-write inside the graph at all — but then the
   graph is not demonstrating the thing you wanted it to demonstrate, it's just
   displaying a string somebody else assembled.

3. **Add something to the engine** — a port that accumulates rather than
   replaces. I'd argue against it: it's a fourth kind of port to hold in your
   head, for one use.

## The runner

12	// Returns the index of the closing 'end' / 'until' that matches the
13	// function body starting at body_start. Tracks nesting depth by
14	// counting block openers and closers. Does not attempt to skip string
15	// literals — good enough for well-formatted source.

17	  const tok = /\b(function|if|while|for|repeat|do|end|until)\b/g;
18	  tok.lastIndex = body_start;

20	  let m;
21	  while ((m = tok.exec(content)) !== null) {
22	    const kw = m[1];
23	    if (kw === 'end' || kw === 'until') {
24	      depth--;
25	      if (depth === 0) return m.index;

27	      depth++;
28	    }
29	  }
30	  return content.length;
31	}

36	// output names. Bare identifiers in the return list become port names;
37	// any complex expression collapses to a single "result" port.
38	function parse_returns(body) {
39	  const re    = /\breturn\b\s*([^\n]+)/g;
40	  const names = new Set();

42	  while ((m = re.exec(body)) !== null) {

51	        names.add(part);

7	// Counts positional args a function references and names them after
8	// any `local var="$N"` assignments. Falls back to generic `argN` when
9	// no local binding is found. Returns an array sized to the highest
10	// `$N` the function touches.
11	function parse_inputs(body) {
12	  const params = {};
13	  const local_re = /local\s+(\w+)\s*=\s*["']?\$\{?(\d+)\}?["']?/g;
14	  let m;
15	  while ((m = local_re.exec(body)) !== null) {
16	    params[parseInt(m[2])] = m[1];
17	  }
18	  if (Object.keys(params).length > 0) {
19	    const max = Math.max(...Object.keys(params).map(Number));
20	    return Array.from({ length: max }, (_, i) => params[i + 1] || `arg${i + 1}`);
21	  }
22	  const seen = new Set();
23	  const pos_re = /\$\{?(\d+)\}?/g;
24	  while ((m = pos_re.exec(body)) !== null) {
25	    const n = parseInt(m[1]);
26	    if (n > 0) seen.add(n);
27	  }
28	  if (seen.size > 0) {
29	    const max = Math.max(...seen);
30	    return Array.from({ length: max }, (_, i) => `arg${i + 1}`);
31	  }
32	  return [];

28	### Decoupling from the editor
29	
30	The editor (phase 2) is being scoped down to a pure map editor — it

32	`last-run.json` is therefore not a UI feed. It exists for:
33

36	- CLI-driven inspection — a future viewer utility (out of scope
37	  here) that pretty-prints the file
38	- Test harness consumption — the integration tests below diff the
39	  written file against expected output
40	
41	Decoupling means the writer's design is driven by these consumers,
42	not by editor rendering needs.
43	
44	### File format: JSON Lines
45	
46	The phase 2 single-document format does not work when the runner is
47	streaming events from many threads. Use JSON Lines instead — one
48	JSON object per line, each line is one event, the file grows
49	monotonically as the run proceeds.
50	
51	Event types:
52	
53	```jsonl
54	{"event":"run_start", "ts":1234567890.123, "map":"maps/classify-demo", "n_workers":16}
55	{"event":"task_submit", "ts":..., "task_id":42, "box_id":"classify", "worker_idx":-1}
56	{"event":"task_start", "ts":..., "task_id":42, "worker_idx":3}
57	{"event":"task_end", "ts":..., "task_id":42, "worker_idx":3, "duration_us":127, "output_size":12}
58	{"event":"slot_alloc", "ts":..., "slot_id":5, "size":256, "n_cells":1}
59	{"event":"slot_free", "ts":..., "slot_id":5}
60	{"event":"run_end", "ts":..., "duration_us":1850, "n_tasks":7}
61	```
62	
63	JSONL is append-only, which makes thread-safe writing tractable: a
64	single mutex around the write call serializes the lines, and each
65	line is self-contained so a partial line on crash is recoverable
66	(reader skips the broken trailing line).
67	
68	The reader (LLM, viewer, test harness) parses one line at a time;
69	total file size doesn't have to fit in memory.

72

74	and outputs are NOT logged by default — for iterator boxes
75	producing thousands of invocations, logging every value bloats

87	
88	A single dedicated writer thread inside the runner consumes events

90	push event records (small fixed-size structs) into the ring; the

93	the only shared state, and a well-written MPSC ring is lock-free
94	on the producer side.

There are actually two separate memory systems that get tangled together in casual talk. Worth pulling them apart first.

**The first system** is for values whose maximum size is known before the run starts. This is the case the design you're remembering was written for. The plan, exactly as you described it: before the run begins, the loader walks the entire graph and lists every distinct value-size that will ever be needed. For each distinct size it builds a separate free-list, pre-populated with enough entries to cover every place in the graph that needs that size. Asking for a value of size N becomes "find the right list, pop one" — no searching, no walks. Giving one back puts it on the same list. The give-back step also peeks at the slot's two physical neighbors in memory; if either neighbor is also free, they merge into one bigger free chunk that goes onto the appropriate larger-size list. On top of all that, a background sweep runs from time to time, walking the whole region opportunistically merging anything that's contiguous and free.

That's the design in full. What's actually in the codebase is much simpler: at startup, the system just asks the operating system for memory one slot at a time and never returns it. The size-class lists and the neighbor-merging — both deferred. The reasoning written into the project is that for the maps the editor produces today, every value lives the whole run anyway, so there's nothing to reclaim and the simple version is fine.

**The second system** is for values whose size isn't known until they're produced. Long text from an LLM, arrays whose length depends on input — anything where the graph can't write down an upper bound. These values don't sit directly in their value slots. Instead, the slot holds a tiny handle (size + pointer), and the actual bytes live in a separate pool.

That separate pool is the thing the developer asking the question cares about, because it's where the long LLM responses on their multi-day runs would accumulate. Today, that pool is dead simple: a chain of fixed-size blocks. When a producer wants to store bytes, it appends to the current block; when the current block doesn't have room, a new one gets allocated; if a value is bigger than a normal block, it gets its own custom-sized block. **Nothing is ever returned to the system mid-run.** The pool grows monotonically until the run ends, at which point the whole thing is freed in one piece.

**On how the loader knows sizes:**

The graph itself carries the answer for the known cases. Every box that produces a value writes down — in its metadata — what size its output is going to be. A box that always emits a 32-byte number declares 32. A box that builds a 4-megabyte image and knows it does, declares 4 megabytes. The loader reads every one of these declarations before the run starts, deduplicates them, and uses that list to set up its pre-warmed pools.

For the unknown case — an LLM call where the response could be 100 bytes or 100 kilobytes, a dynamic array whose length depends on input — the box just declares "size not known." When the loader sees that, it doesn't pre-warm a pool for that box; it knows the value will need to be allocated on demand when the box actually produces something.

Both kinds of value come out of the same underlying memory. The difference is just whether the loader had a pool ready for that size or not. A known-size value pops from its pre-warmed list — one step. An unknown-size value goes through a path that says "find me the smallest free region that fits, slice it if needed, give me back the front." Same allocator, two doors. The unknown-size door is slightly slower per allocation, but that cost is dwarfed by whatever produced the value in the first place (the LLM call itself, the array construction).

The case you raised — known-at-compile-time large allocation — is fully covered by the first door. There's nothing special about "large" here. The free-list approach treats a 4-megabyte size class no differently than a 32-byte size class; just a different list.

**On deterministic sweep triggers:**

Two natural moments. Both are decoupled from wall-clock time.

The first is the moment an allocation request can't be satisfied from any existing free-list. This is the obvious one — the system knows it's about to fail. Before it gives up and asks the operating system for more memory, it runs the sweep to consolidate any fragments that the cheap neighbor-merge didn't catch. If the sweep produces enough contiguous space to satisfy the request, the allocation succeeds and the heap doesn't grow. If it doesn't, only then does the system ask the OS for more. This makes the sweep the immediate alternative to heap growth — which is exactly when its work has the most value. It's also fully deterministic: same allocation pattern, same sweep moments.

The second is quiescence — moments when nothing is running. The runtime already recognizes these moments because it uses them to decide a run is complete. Between batches is a natural opportunity because no tasks are reading or writing chunks at that instant, so the sweep can be more aggressive without coordinating with anyone.

I'd start with just the first. It's the mandatory one — it's what stands between "allocation failed" and "ask the OS for more memory." The second is opportunistic and can be added later if profiling shows fragmentation is sneaking through.

A third option just to name it: trigger the sweep when the count of small free fragments crosses a threshold (an obvious sign of splintering). Deterministic, but needs tuning the threshold, and the first option covers most of the same ground without that work.

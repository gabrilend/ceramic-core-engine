## Your model of it is right, with one correction

You said: take a map file and compile it, pulling in the functions it
references. Yes — and "pulling in" is literal. The generator reads the map,
sees `station adder math.c:add p`, and writes an emitted C file that does two
things: it `#include`s `math.c` **whole**, so the compiler can see the real type
declarations, and it writes out a call that places a station running `add`.

That whole-file include is why `sizeof` works at all. `sizeof` is a compile-time
operator — the compiler evaluates it and burns a literal into the machine
code. A running program has no types left, so you cannot hand it the text `vec3`
and get 12 back. Including the source makes the types visible at the moment the
generator's output is compiled, and only then does it write `sizeof a0`.

## What does the compiling

**Your ordinary C compiler**, at two different moments.

**At build time**, three steps:

1. Compile the generator from `scripts/*.c` → an executable.
2. Run it over your box sources and your map → one C file.
3. Compile and link that file, plus `cera.c`, plus your own `main`, with
   `--dynamic-list` and `--gc-sections`.

**At run time**, only when a program is handed a description it was not built
for. Then the engine shells out — `src/cera.c` around line 8640 builds the
command string and runs it, invoking the generator and then the compiler to
produce a shared object it opens.

**Which compiler is decided at build time and recorded.** Four values are baked
in as `-D` definitions when `cera.c` is compiled:

- `CERA_CC` — the compiler that built this binary
- `CERA_GENERATOR` — the path to the generator executable
- `CERA_INCLUDE` — where `cera.h` lives, so generated code can find it
- `CERA_RAM_SHARED` / `CERA_RAM_EXEC` — the two scratch tiers

The point of recording the compiler rather than looking one up: a box compiled
next year must agree with a box compiled today about what `sizeof` returns.
Using the same compiler makes that true by construction instead of by checking.

## The part worth knowing

**A program whose map only names boxes already in the binary never invokes a
compiler at all.** It ships as one executable, with its own C source text
carried inside it as string arrays, and runs on a machine with no toolchain. The
runtime compiler is needed precisely when genuinely new code is arriving — a
map you were not built for, or a box compiled while you run.

So the answer to "is `cera.c` and `cera.h` all we need" depends on who is
asking. To *run* a finished soramech: yes, and not even that — just the
binary. To *build* one: those two, the export list, and the generator's source.

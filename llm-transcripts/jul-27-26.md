## 1. Worker-side gathering


**What it changes, in one sentence:** today the gathered values are pulled *when
the task is assembled*, by whichever thread delivered the completing value; you
want them pulled *when the task begins running*, by the worker that picked it
up.


**How it works now.** When a delivery completes a station's input set, the
delivering thread claims the buffered values under the station's lock, releases
the lock, and then builds the task — and *during that build* it runs every
gathered source inline, on its own stack, before the task ever reaches the pool.
So a burst that enqueues a hundred tasks pays a hundred gathers serially on the
delivering thread. The first-pass report caught exactly this: our phase 4 demo's
timing was wrong at first because seeded values paid their gather cost on the
*seeding* thread, before the measured window even opened. Your proposal
parallelizes that cost across the pool and shortens the hot path. It also makes
values *fresher* — read at the moment of use rather than at the moment of
scheduling — which is arguably more faithful to the pull path's own philosophy
than what I built.


**The good news: your "generator function" already exists, generically.** The
issue worries that each box might need its own gather-filling code since the
same function can be wired three different ways at three stations. But wiring
lives on the *station*, not the box: each slot record carries a one-byte kind
tag and, for gathered slots, the source station index (an `int`). The task
already carries which station it belongs to (an `int32`). So one engine function
can do the fill for every box that will ever exist: walk the station's slots,
and for each slot tagged "gathered," run its source inline into the task's
already-reserved value bytes. No per-box generation, no macro — the same trick
as the readiness dispatch.


**What the task struct needs** (current fields, plus the two candidates):


| field | type | status |

|---|---|---|

| call | function pointer, `void (*)(task_t *)` | exists — the shim |

| station | `int32_t` | exists |

| port | `int32_t` | exists |

| n_in / in / out | `int32_t`, `void **`, `void *` | exist — value pointers into the task's own tail block |

| **prepare** | function pointer, or a one-byte flag | new — null/zero when nothing to gather; the worker runs it before the shim |

| **map** | pointer to the owning map | new — and this is the catch |


The catch is that last row. The fill function must reach the station table, and
a task carries no route back to its map. Statics writes and statistics already
hit this same wall and got the process-global "active map" workaround, with its
silent one-map-per-process restriction. This issue is the third customer, and
I'd say it tips the decision: thread the map pointer through the task
(second-pass priority #2 in the report) as part of this work, rather than
leaning on the global a third time.


**What gets replaced or updated:** the task struct and one line of the worker
loop (run prepare, then call); the task-construction step in the delivery file
(stop pulling gathers there, set the prepare marker instead); the gather
module's timing attribution (still charged to the pulling *station*, but now
measured on the worker — which actually simplifies the story issue 702 tells);
the seed sweep gets faster for free (seeded gather-heavy stations currently pay
all pulls serially on the load thread); docs 004's sentence "at the moment a
task is being assembled" becomes "at the moment the invocation begins"; and the
freshness test's phrasing, though its assertions still hold.


**One hazard I found while thinking this through — an existing latent race,
not one you'd introduce:** the runtime gather-repoint added in phase 7 mutates a
slot's source under the station's lock, but the gather walk *reads* that source
without any lock. Today the window is small; deferring the read to the worker
widens it to the full queue latency. Whatever we choose has to make "read the
gather wiring" and "repoint the gather wiring" agree on a lock or an atomic.
Deferred gathering also changes what a repoint *means*: a task enqueued before
the rewire would gather from the **new** source when it runs. I think that's
correct — "true at the moment used" — but it's a semantics decision, not an
accident, so it should be written down.


**Questions back at you:**

- Should statics defer the same way? They're claimed at assembly too, under the

  simple ("ring values are claimed at readiness; everything else resolves at

- Is deferral the only mode, or per-slot? A slot could conceivably want

## 2. Station-table growth (the 704 follow-up)


**What it changes, in one sentence:** the one structure the whole engine
promises never moves — the flat station array — becomes movable, so stations
can be added at runtime.


Here's the tension, as two facts that are both true: *every wire survives a
reallocation, because wires hold indices, not pointers* — and yet
*reallocation breaks running code anyway.* How can both be so? Because threads
mid-operation hold `&stations[i]` on their stacks: the delivery walk keeps a
station pointer across its lock-write-check sequence, and the gather walk holds
one while running user code. Indices survive the move; those in-flight pointers
don't. That's the "every thread needs to see the new base" sentence you quoted.


**Your double-buffer copy has a hidden ally in the existing design.** A station
record is deliberately fixed-size, with everything variable — slot arrays,
ring storage, port lists — hanging off pointers. So copying a station row
copies *pointers to* the live buffers, not the buffers: the old array and the
new array are two views of the same mutable state, and the copy doesn't race the
data at all. "Mostly static, take our time" is exactly right for the rows.
**Except for one field:** the lock itself is embedded *inside* the row. After a
copy there'd be two locks claiming to guard one slot array — a deliverer
through the old base and a deliverer through the new base could both "hold the
mutex" and interleave freely. Mutual exclusion quietly dies.


So the integration move I'd propose is to finish the thought the original design
started: split the station into a **row** (what the table holds:
index-addressable, copyable — the shim pointer, kind, sizes, a pointer to the
body) and a **body** (separately allocated, *never moves*: the mutex, the slot
array, the ports, the iterator cursor, the statistics). Growth then copies rows
freely; every lock and every buffer keeps its address forever. This is your
"move the pointer in the box station list to point to the correct location,"
made concrete.


**Retiring the old array:** rather than reference-counting readers (real RCU
machinery), I'd keep every superseded array on a retired list and free them only
at map teardown. Growth doubles, so a map that grows from 8 to 8,192 stations
leaks ten small arrays of stale rows — a few kilobytes, bounded by the
logarithm, in exchange for deleting the entire "when is the last reader gone"
problem. Same bargain the ring buffers already made ("growth happens at most a
couple dozen times in a process lifetime").


**The raise-your-hand ring** — your queue of guests who want to add a station
while construction runs — fits naturally *here*, and I'd note the pool's task
ring is already the template for it, as you say. But I'd push back gently on
generalizing it to the other growable lists: the task ring and the slot buffers
grow under locks nobody holds for longer than a bounded memory copy, and nothing
points into either one — their growth is already safe and brief. The station
table is the one structure whose readers hold no lock at all, which is precisely
why it needs the fancier pattern. Adopting the pattern where reads are lockless,
and leaving the short-lock structures alone, keeps each mechanism as simple as
its actual problem.


**What gets replaced or updated:** the station struct splits (the header's
biggest change since phase 2); every direct `stations[i]` access across the
engine — delivery, statics, gather, loader, validation, seed, dump, rewire,
observers — goes through a small accessor that acquire-loads the current base
(wide, but purely mechanical; a grep-driven sweep); the station count becomes
something read once per operation rather than assumed constant; teardown learns
the retired list; and docs 002's "allocated once and never resized" becomes "the
lookup table may move; the state it points at never does." The map format,
registry, and generator are untouched — runtime adds come from the control
surface, and the dump already describes whatever the live table holds.


**Question back:** when a *new* station is added mid-run, it arrives with no
name from any file and possibly a box the map never mentioned. The dump is
supposed to be "the only accurate description of what is running" — what
should it print for a station born at runtime? (I'd suggest the adder must
supply a name, same rule as the loader: everything speakable.)

### Assistant Response 6

Almost the same page — but you've actually gone a step past what I proposed,
and your version is better. Let me draw the line between the two precisely,
because the difference matters for what gets touched.


**What I had sketched:** one trip through the pool. The incomplete task goes
into the queue immediately; the worker that picks it up runs a "prepare" step
(gather everything) and then the box, in one pickup. That needs a new field on
the task struct and a new line in the worker loop — the pool learns something.


**What you're describing:** two trips. The enqueueing thread pops the ring
buffers, copies the statics, and then — instead of pushing the box task —
pushes a *different, specialized task* whose job is to finish the first one. A
worker picks up that gather task, runs the gather boxes in order, writes their
outputs into the waiting task's input slots, and then pushes the now-complete
task itself. The delivering thread moved on long ago, exactly as you say.


Yours wins on three counts, and one of them dissolves a problem I flagged last
time:


1. **The pool stays completely ignorant.** A gather task is just a task — the
   pool runs its function pointer like any other. No prepare hook, no new
   worker-loop branch. The specialization lives entirely inside what the gather
   task's `call` points at.

2. **The box task stays completely ordinary.** By the time it's enqueued it is a
   plain, fully-materialized task, indistinguishable from one that never had
   gather inputs. Tasks with only ring and static slots take today's exact path
   with zero added cost.

3. **The context problem evaporates — locally.** My version needed the task to
   carry a map pointer (or lean on the process-global active map a third time).
   In yours, the *wrapper* is built by the engine at claim time, so the engine
   can stash the map pointer inside the wrapper itself. No global, no
   task-struct change, no pool change. The larger "engine has no context" thread
   still exists for statistics and statics writes, but this feature no longer
   forces it — which reorders my earlier sequencing advice: gathering no
   longer waits on that work.


Concretely, the gather task would be a small struct with a task embedded at its
head — the same trick the phase 1 tests use, so the pool cannot tell:


| field | type | meaning |

|---|---|---|

| base | task struct (embedded first) | its `call` is the gatherer handler; its station field is a sentinel, minus one — "belongs to no station" |

| map | pointer to the owning map | how the handler reaches the station table; carried here, not globally |

| pending | pointer to the waiting task | the task being completed; ownership is here, as you said |

| n_gathers | `int` | how many slots below |

| gathers[] | array of { slot `int`, source `int` } | which input slots to fill, from which upstream stations, in order |


One clarification on your phrase "generated for each task": this is
*instantiated* per task, not code-generated per box. No generation is needed —
the wiring lives on the station's slot records, and the waiting task already
reserves the right number of bytes for every input, so one handler function
serves every box that will ever exist: walk the array, run each source inline
(chains recurse exactly as they do today, just on the worker's stack now), copy
each result into the pending task's slot, then push the pending task.


Now the details that need deciding — the "what gets replaced" of it:


**The free-after-run contract is why the wrapper should be a separate
allocation.** The worker loop today is unconditional: run the task, hand it to
the delivery hook, free it. Your phrase "the gatherer handler utility *on the
task struct*" could be read as the pending task carrying its own handler and
re-pushing *itself* — one allocation, the task's `call` swapped from handler
to shim between trips. That's elegant, but a self-re-enqueueing task gets freed
by the worker that just ran its gather phase, while it sits in the queue — the
pool would need a "don't free me this time" signal, which breaks the one
contract it has. The separate wrapper keeps it whole: the wrapper is run,
finished, and freed normally; the pending task is pushed by the handler and
freed after *its* run. Cost: one small malloc per gathered task. The delivery
hook needs one line — a task whose station is the sentinel is machinery, not a
box run: skip delivery, skip the run counter.


**Take the gather snapshot under the station's mutex, during the claim.** This
closes a latent race I found last time: the runtime gather-repoint mutates a
slot's source under the station lock, but today's gather walk reads it with no
lock. If the claim step — which already holds the mutex — copies the {slot,
source} pairs into the wrapper right there, the race is gone entirely, and the
semantics become crisp: *wiring as of scheduling, values as of gathering.* A
repoint after enqueue doesn't touch tasks already in flight.


**Serial or parallel gathers per task?** You settled on "array of gather boxes
to run in order" — one wrapper, gathers run serially on one worker. I agree
for the first cut: the win we're buying is "the delivering thread pays nothing,"
and that's fully bought. The alternative — one pool task per gather slot,
outputs aimed at the pending task's slots, last one to finish enqueues it — is
exactly your opening sentence, and it parallelizes *within* one task's assembly,
but it needs an atomic countdown on the pending task and a rule for who pushes.
Worth having as a later option for tasks with several slow gatherers; not worth
the machinery now, since gathers across *different* tasks already parallelize
(each task's wrapper lands on its own worker).


**Statics: agreed, and it settles my earlier question.** Filled directly at
build time, under the statics lock as today — so a threshold written mid-run
is seen by the *next task built*, not by tasks already queued. That keeps the
existing mutation semantics and test exactly as they are.


**Smaller consequences, so nothing surprises us:** queue traffic doubles for
gathered tasks (two entries instead of one — the ring doubles itself,
demonstrably cheap); a gathered task waits in the FIFO twice, so its latency
rises while throughput doesn't; assembly order across tasks is no longer gather
order, which nothing ever promised; the seed sweep gets genuinely faster, since
seeded gather-heavy stations currently pay every pull serially on the load
thread before release; the gather-time statistic moves into the handler and
stays charged to the pulling station — the attribution story actually gets
simpler; and a gatherer that aborts (missing file) now dies on a worker instead
of the deliverer, which is the same program-stopping behavior from a different
thread. Docs 004's "at the moment a task is being assembled" becomes "when its
gather task runs," and the completed gathering issues get their current-behavior
sections updated.

1. **Wrapper as separate allocation with the sentinel-station rule — agreed?**
   It's the version where the pool's run-finish-free contract stays untouched;
   the price is one small allocation per gathered task.

2. **Do you want the parallel-per-slot variant designed into the issue as a
   stated future option** (the atomic-countdown shape), or left out entirely

# Your initialization question


## The startup you described already exists — twice


The graph loader has a routine that computes exactly the set you described. It
walks every box and keeps the ones where:


- the box is a **call** or **write** box (a read box is a value source, never a
  task), **and**

- every non-optional input port has zero *non-read* feeders — meaning nothing
  upstream has to compute before it can fire


A box with no inputs at all passes vacuously. It stores the result as a plain
array of box indices on the graph.


**Nothing in the runner reads that array.** Its only consumers are two unit
tests. What the runner actually does at startup is ignore the precomputed list
and sweep *every* box, asking each "are you ready?" — which recomputes the
same answer a second time, with different code, in a different file.


So the first thing initialization should do is stop doing this twice. My
recommendation: keep the loader's version, because a rule stated once in a named
routine is testable and a rule embedded in a sweep loop isn't, and have the
runner submit from that array.


## It's already asynchronous, and here's what makes that safe


The workers pass their initialization barrier and enter the task loop *before*
the sweep starts. So the picture you described — one thread checking boxes
while others already process — is what happens today. The main thread sweeps;
workers are already draining.


What makes it safe is a per-box atomic flag, one integer per box, set by
compare-and-swap. A box can be found ready at the same instant by the sweeping
thread and by a worker that just pushed a value into it. Both call
spawn-if-ready; the compare-and-swap lets exactly one win.


**If you parallelize the sweep across several threads, that flag becomes the
only thing standing between you and duplicate execution** — and multi-spawn
boxes (iterators and everything downstream of one) *deliberately bypass it*,
because they're supposed to re-fire on every push. So those would need a
different guard before the sweep could be split. That's the one real hazard in
the plan you sketched.


## Two things must finish before the sweep, in order


**Slot allocation.** Every box's input ports get numbered cells in the shared
store. Sizing the store needs the complete box list, so this is inherently
single-threaded and inherently first.


**Literal push.** Any input port carrying a constant value gets that constant
written into its slot. This must complete before *any* readiness test runs —
otherwise a box whose only input is a hard-coded number looks un-ready, gets
skipped, and nothing ever pushes into it, so it never fires. Silent no-op, no
error.


## Where your model differs from the code: the disk reads


You said readiness is satisfied "usually by reading something from disk." That's
not what happens, and this is the interesting part.


Read boxes never enter the thread pool at all. Their files are read **during
graph load** — a plain single-threaded read, before the pool exists — and
the bytes are cached on the box. A consumer fed by a read box copies from that
cache when it fires.


So:


- A box fed only by read boxes counts as ready with **zero** I/O happening at
  readiness-check time.

- **All of the file reading is serialized, ahead of everything.** A map that
  reads twenty files does twenty sequential reads before the first worker gets a
  task.


That's the actual serial bottleneck at startup, and it's upstream of the sweep
you were thinking about parallelizing. The sweep is cheap — it's integer
comparisons against slot state. The reads are the expensive part and they're the
part that isn't parallel.


## What readiness actually tests


For each input port of a box, skip it if optional; otherwise ask whether its
slot holds a value. The fields involved:


| field | type | meaning |

|---|---|---|

| number of inputs | `int` | how many input ports the box declares |

| per-port optional flag | `int` (0/1) | 1 means the port is skipped entirely when testing readiness |

| per-port slot id | `int` | index into the shared slot store where this port's value lives |

| per-port slot mode | enum: POP or PEEK | POP consumes the value when read; PEEK leaves it in place, so it doesn't gate re-firing |

| multi-spawn flag | `int` (0/1) | 1 means re-spawn on every push instead of once per run; bypasses the duplicate guard |


That's the whole test. No type checking, no reachability check, no cost
estimate.


## Four things initialization should do and doesn't


**1. Deliver a "nothing could start" verdict.** If the sweep finds zero ready
boxes, the pool quiesces immediately, the runner prints `run complete (0
task(s))` and **exits zero**. A map that cannot start is indistinguishable from
a map that ran. This is the highest-value addition and it's about ten lines.


**2. Deliver a "not everything finished" verdict.** After quiescence, nothing
compares the set of boxes that fired against the set that exists. A graph that
stalls halfway — a fan-in box waiting forever on a second input that never
arrives — reports success. The runner counts dispatched tasks but never
compares that count to anything.


**3. Order the submissions.** Every startup spawn passes priority zero, but the
pool accepts a priority. If one ready box is a slow model call and thirty are
cheap string operations, submitting the slow one first is free wall-clock
(longest-processing-time-first). You'd need a cost hint on the box to do it
properly — but even "boxes whose language spec is expensive to enter go first"
would help.


**4. Parallelize the read-box loading**, per the section above — that's where
the serial time actually is. The trade-off worth stating: reading every read box
eagerly reads files that no execution path may ever reach. Today's serial load
already pays that cost, so parallelizing it is strictly better; making it *lazy*
would be a different and larger change.

# The other structural findings


## 1. Two execution engines that no longer speak the same language


This is the big one, and it's the entry-point problem generalized. The
interpreter and the pool runner accept the same file format and implement
**different semantics**:


| | interpreter | pool runner |

|---|---|---|

| entry points | exactly one, from the declared field | as many as it infers |

| times a box can fire | **at most once, ever** (a visited flag) | unlimited; re-spawns on every push |

| optional input ports | **not implemented** — every declared port must have a value | skipped when testing readiness |

| output capacity | not implemented | read from the box, sizes the slot cells |

| read boxes | not implemented as a kind | pull-on-demand cached value sources |

| cycles | impossible — the visited flag forbids re-entry | the normal case |


The interpreter's queue is seeded with a single box id. **If the declared entry
is empty, the queue is empty, the loop never runs, and the map reports success
having executed nothing.**


Run narrative-engine's map through the interpreter and all three of these hit at
once: empty entry (zero boxes execute), optional ports (three of them, which
would make that box permanently un-ready), and a loopback (the whole point of
the map). It would report success.


Its companion doc still describes the box-invocation call as "the future thread
pool swap point." That future arrived as a separate C program eighteen months of
commits ago, and the interpreter was neither updated nor retired. It is the
default runner in `demo.sh`.


**This needs a ruling more than the entry point did:** is the interpreter a
supported second engine that must reach parity, or is it phase-1 scaffolding to
be deleted? Right now it's neither, and "neither" means a map author can get
silent success from a map that never ran.


## 2. A required file that the real runtime never opens


`drivers.json` maps a file extension to a driver script. The schema
**hard-requires** it. The map-creation script writes one. The validator refuses
any map lacking one.


**The C pool runner never opens it.** It resolves languages through the
per-language specs under `langs/`. Consequently all 27 tracked map fixtures —
the ones the runtime actually executes in the test suite — omit it, and the
validator rejects all 27 on that basis alone.


So new maps are born carrying a required file for an engine that may be on its
way out, and the maps that actually run don't have it.


## 3. A field one engine reads and the other doesn't know exists


A box may carry an explicit `lang` field. The C loader reads it, and **falls
back to guessing from the ref's file extension** when it's absent — silently,
with no warning emitted. The Lua schema never mentions the field at all: it
neither requires nor validates it.


narrative-engine writes it explicitly on every box. So a downstream project is
depending on a field that SoraMech's schema doesn't document and its validator
would ignore.


Two problems in one: an undocumented field, and a silent fallback. By your own
rule that fallback is a warning, and warnings are errors.


## 4. The validator/runtime rule-set split


Covered in the issue file now. The measurement: **it accepts 0 of the 27
fixtures the runtime runs**, and it crashes with a Lua traceback rather than a
report when handed a current-format map.

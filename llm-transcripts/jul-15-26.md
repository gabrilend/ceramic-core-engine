## Why you can't just point LuaJIT at a memory location and call it a variable


Your instinct is right for *part* of the data and impossible for the rest, and
the dividing line is the whole story.


**What a `lua_State` actually is.** Each box that runs Lua runs inside a
`lua_State` — LuaJIT's interpreter context. A `lua_State` owns three things: a
value stack, a global table, and a *garbage-collected heap* of every
table/string/closure that code created. In the pool, boxes on different worker
threads sit in *different* `lua_State`s. That's not incidental — it's what
lets them run at the same time without a global lock.


**A number is a memory location. A table is not.** A Lua number or boolean is a
*value* — 8 bytes, no pointer, lives inline on the stack. You genuinely *can*
point the other state at those 8 bytes and say "that's yours" — copy them
across and they're a valid number over there. **That is exactly what the fast
path does** with `lua_tolstring` for primitives and short strings: it hands over
a copyable byte blob. No JSON, no walking, basically free.


A table is a different animal. It's a `GCtab` struct with an *array part* and a
*hash part* — two C arrays that LuaJIT `malloc`'d inside **this** state's
allocator, and every slot inside can point at yet another GC object in **this**
state's heap. So "the memory location of the table" is really a little web of
pointers that only mean anything relative to the heap that owns them. Hand that
pointer to state B and three things go wrong at once: B's collector has never
heard of it and may free the memory out from under it; A's collector may move or
reclaim it while B is mid-read; and every internal pointer B follows is reading
*A's* heap, which A is free to collect at any moment. That's use-after-free
across two garbage collectors. LuaJIT doesn't forbid sharing GC objects between
states because someone forgot to implement it — it's a memory-safety
invariant. There is no pointer both collectors agree on, because a table is
*defined relative to the heap that owns it*.


So "don't worry, we translated it into something Lua can read" — that
translation **is** serialization. The only representation two independent heaps
can both read is a flat, copyable byte buffer. JSON is one such buffer. There's
no third option that's a pointer.


**Effil doesn't escape this — it confirms it.** Effil is built for exactly
cross-Lua-thread data, and under the hood `effil.channel`/`effil.table`
*deep-copy* across the boundary: primitives inline, strings copied, nested
tables rebuilt slot by slot. The specialist library pays the copy too; it just
hides it behind a nicer API. Adopting it wouldn't delete our JSON step — it
would rename it. And critically for the fear in your writeup: **the
synchronization stays the runtime's job either way.** Channels *are* the
dispatch/slot layer. A box author never writes a line of thread-sync; they
return a table and receive a table. So "the user would have to define
multithreading in the language spec" was never on the table.


**The one way to pass a table by reference is to not cross the boundary at
all.** That's issue 313's whole-program merge: when a run of boxes is provably
all-Lua and can be scheduled together, compile them into *one module in one
`lua_State`*, and the wire between them collapses into an ordinary function
return → function argument. A real pointer pass, zero copy — precisely
because there's no second heap to translate for.


**So your "it's just an organization system, not a speed improvement" conclusion
is half true.** For primitives the fast path is a real win — memcpy of a few
bytes instead of building and parsing a JSON document. For *tables* you've put
your finger on something real: across a state boundary there is no free lunch.
You either serialize (copy) or merge (co-locate). The lever that actually
removes the table copy is 313's merge — and that's a *scheduling* decision,
not an encoding trick. The deep tension is: **by-reference speed requires
co-location (one state, one thread); parallelism requires separation (many
states, must copy).** You cannot have both on the same wire.

- The fast path isn't "broken," it's a **correct optimization of the case it can
  cheaply serve** (primitives) that **silently no-op'd the case it can't**
  (tables). The bug is the *silence*, not the tradeoff — a table on a

  into one state (ceiling), never drain to zero bytes.

- "By reference" in a threaded system is a **scheduling property, not a
  data-format property.** You get zero-copy only by refusing to cross a heap
  boundary; the moment two boxes are on two threads, "reference" is meaningless
  and only bytes travel.

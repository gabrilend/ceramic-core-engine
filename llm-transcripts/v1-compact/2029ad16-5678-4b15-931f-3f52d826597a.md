**1. Server spawns a separate runner process (recommended).** The HTTP server handles only file I/O (read/write box files) and process management. When the user hits "run", the server execs `luajit soramech-runner.lua <map-dir>` as a child process and streams its stdout back to the browser over SSE (server-sent events — a one-liner in luasocket, no WebSocket complexity). Multiple maps run as separate processes in parallel naturally. The runner can also be invoked from the command line without the UI at all.

**2. Server runs FSM inline as a coroutine.** Simpler to set up but the FSM shares the server process. A runaway FSM blocks file saves. Harder to kill a specific run without affecting others.

**3. Fully detached runner, server watches a pipe.** Most decoupled but unnecessary complexity for v1.

## Assistant

The difference is **who owns the runner process**.

In **option 1**, the server forks and execs the runner as its child process. The OS gives you a pipe to its stdout for free. The server knows the PID, can kill it, can wait for it to finish, and gets notified when it exits. Standard parent-child relationship.

In **option 3**, the runner is launched independently — not a child of the server. It could be started by the user from the terminal, a cron job, another process, anything. The server has no handle on it. The only shared channel is something both parties agree to watch: a file in `/tmp/`, a named pipe (FIFO), or a unix socket. Server polls or `inotify`s the file to know when new output arrives.

**Option 3 is useful when** you want the runner to outlive the server, survive a server restart, or be triggered by something other than the UI. It's also the pattern if the runner is a long-lived daemon rather than a one-shot process.

**For us, since output just goes to files anyway**, the distinction mostly collapses. Option 1 is cleaner for v1: server spawns runner as a child, knows when it's done or crashed, can report that status back to the UI ("run finished" / "run failed with exit code 1"). The runner writes its outputs to `output/data/` and its logs to `tmp/`. The server doesn't need to proxy anything — it just tracks process state.

Option 3 becomes relevant later if you want to run a map headlessly from a cronjob and still have the UI reflect its status. We can add that without changing the runner — just add a lock file or status json the runner writes to that the server can read on demand.

## Assistant

`src/004-executor.lua` is the runtime engine for SoraMech — the thing that actually *runs* a map you've built in the editor.

When you invoke `soramech-runner.lua` on a map, the executor:

1. **Loads the graph** — reads all the box JSON files, the connections between them, and the driver table
2. **Pre-seeds the store** — a flat key-value table keyed by `"box_id.port_name"`. Literal values you set in the inspector get written here before anything runs
3. **Starts at the entry box** — whichever box is flagged as the entry point, it gets queued first
4. **Works through the queue** — for each box:
   - Checks whether all its input ports have values in the store (`inputs_satisfied`)
   - If yes: calls the appropriate language driver (lua, bash, etc.), gets back the output values
   - Pushes those outputs into the store under the target box's input keys
   - Enqueues any downstream boxes that are now fully satisfied
5. **Branch boxes** are special — they don't call a driver, they just look at their single input value and route it to the matching output port based on predicates (eq, contains, etc.)

So in terms of dataflow: the store is the "wire memory." A wired connection writes a value into `"to_box.to_port"` at runtime. A literal value pre-writes into `"box_id.port_name"` before the loop. If a wire later fires to the same key, it overwrites it — wires win.

The executor is currently synchronous (one box at a time, in queue order). The comment at the top of `run_task` marks it as the future thread pool swap point — when multiple boxes are independently ready, they'd be handed off to worker threads instead of run in sequence.

## Assistant

The `ollama.lua` call box and the `llm-route` box solve different problems, and the executor treats them very differently.

**`call` box using `ollama.lua`:**

The executor doesn't know or care that it's talking to Ollama. It just sees a box with `kind: "call"`, looks up the driver (`drivers/lua.sh`), spawns a subprocess, passes the inputs as JSON arguments, and collects the return values as named output ports. The executor's job is done after the function returns — it pushes the output values into the store and enqueues whatever downstream boxes are now satisfied.

**`llm-route` box:**

The executor handles it directly in `fire_connections` without spawning any subprocess. There's no driver involved. Instead, when the box runs, `llm_route_call()` in the executor itself calls `require("ollama")` and makes the Ollama request inline in Lua. The result isn't an output value pushed to downstream ports — it's a **routing decision**. The executor looks at which output port name matches the LLM's reply, then fires only that port's wire, passing the original `text` input through as the value. The other ports stay silent.

So the key difference is **data flow vs. control flow**:

- `call` box: produces output values, all wired outputs fire, downstream boxes receive data
- `llm-route` box: produces no data of its own, exactly one output wire fires, that wire carries the input text through — the box is a switch, not a transformer

It's the same distinction as between a `call` box and a `branch` box.

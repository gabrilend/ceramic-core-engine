### What 307 typed C wrapper generation would do

Today, a C-box author has to write a function that takes SoraMech's bytes-in / bytes-out ABI — they receive a packed byte buffer of inputs and have to deserialize, do the work, and serialize the return. The author writes the marshalling boilerplate for every box.

307's typed wrapper proposes that the author write a **natural C function with normal typed arguments and a normal return value**:

```c
// user writes this — no SoraMech-specific anything:
int classify(const char *text, int weight) {
    if (text[0] >= '0' && text[0] <= '9') return weight * 1;
    return weight * 2;
}
```

…and declares the signature in the box's JSON:

```json
{
  "id": "classify", "lang": "c", "ref": "classify.c", "fn": "classify",
  "inputs":  [{"name": "text", "type": "string"}, {"name": "weight", "type": "int"}],
  "returns": "int"
}
```

The C spec then **generates a wrapper `.c` file** at compile time that bridges SoraMech's ABI to the user's natural function:

```c
// auto-generated:
extern int classify(const char *, int);
int sm_box_entry(const uint8_t *in_buf, uint32_t in_size,
                 uint8_t *out_buf, uint32_t out_cap, uint32_t *out_size) {
    // unpack `text` as null-terminated string and `weight` as int from in_buf
    // call: int r = classify(text, weight);
    // serialize r into out_buf, set *out_size
    return 0;
}
```

The wrapper plus the user's `.c` get compiled together; the spec always `dlsym`s `sm_box_entry`. The huge wins:

1. **Library functions become boxes with no glue code.** A box can declare `"fn": "compress2"`, `"headers": ["<zlib.h>"]`, `"link_libs": ["z"]` and call into zlib directly with no user-written `.c` file at all. Same for OpenCV, libcurl, JSON-C, etc — any C library with a header.
2. **Type safety at compile time.** Mismatch between declared `inputs` and the actual function signature surfaces as a gcc error in the generated wrapper, not a runtime crash.
3. **Idiomatic user code.** The user's `.c` looks like ordinary C — no `int box(SM_BOX_ARGS)` macro, no extracting from a buffer, no laying-out a return.

The remaining piece is essentially a small code-generator that knows the type system: `string` → `const char *`, `int` → `int32_t`, `double` → `double`, `bytes` → `const uint8_t *, size_t`, and so on. Compile cost is one extra gcc invocation per C box per build.

### 312 — how the dynamic dispatch actually works

You asked: *how are we planning to dynamically do this? are we requiring the spec to explain how?*

Yes — **the spec explains how, completely.** The dispatch layer is generic; it only knows which callback to call based on a single bit on each box. Here's the shape:

**The spec contract has three layers of invocation:**

```c
typedef struct {
    /* The universal fallback. JSON-in, JSON-out. Every spec must
     * implement this — it's the cross-language lingua franca. */
    int (*invoke)(handle, fn, in_json,  in_size,  out_json,  out_cap, out_size);

    /* The fast path. The spec defines what "native" means for
     * itself — a Lua spec might pass values via the worker's
     * lua_State, a C spec might pass typed structs, a future
     * msgpack-aware spec might pass packed binary. Optional;
     * NULL means "no fast path available, always go through invoke". */
    int (*invoke_native)(handle, fn, native_in, in_size, native_out, out_cap, out_size);

    /* The bridge. Used at language boundaries: a Lua producer
     * feeding a C consumer goes Lua-native → JSON → C-native. */
    int (*native_to_json)(...);
    int (*json_to_native)(...);
} lang_spec_t;
```

**The dispatch's role is purely routing**, not optimization. At graph load (already implemented per the 312 fast-path classification work), each call box is tagged with a single bit: `use_native_invoke`. The bit is true iff every input slot feeding this box is produced by a same-language box AND every output of this box feeds only same-language consumers — i.e., this box sits inside a same-language island.

At dispatch time, the resolution is one if-else:

```c
lang_invoke_fn fn = b->use_native_invoke && spec->invoke_native
                    ? spec->invoke_native     /* binary native format */
                    : spec->invoke;           /* JSON */
```

That's it. The dispatch doesn't know what "native" means for Lua vs C vs Bash — it just trusts that if two boxes have the same spec and the box's bit says native, the producer-side native output and consumer-side native input speak the same private dialect.

**What each spec must declare:**

- A stable binary serialization of its native values that producer-side `invoke_native` writes and consumer-side `invoke_native` reads. This is the bit the spec authors design themselves. Examples of what a spec could pick:
  - **Lua**: a length-prefixed binary table dump (table → repeated `{key_size, key_bytes, value_kind, value_bytes}`). Faster than JSON because no string parsing, no escape decoding, types are tagged inline.
  - **C**: raw memcpy of the declared struct layout (the wrapper from 307 knows the type). Zero serialization — just bytes on the wire.
  - **Bash**: arguably no fast path makes sense; bash always deals in text. The spec leaves `invoke_native` as NULL and the dispatch falls through to `invoke` (which is JSON, which is fine — bash boxes are slow regardless).

The dispatch doesn't pick the format. The spec author picks the format. The dispatch just routes through whichever callback the spec advertises.

This is the same pattern issue 317 uses for data boxes: the spec is the only thing that knows how to convert between native and JSON; the runtime is the conductor that calls the right baton-handoff at the right moment.

## Assistant

307's promise is the same rule 317 enforces, just for *call* boxes instead of data boxes: **the box author writes idiomatic code in their language, and SoraMech adapts to it.**

### What 307 is for

Today a C-box author has to write a function with the SoraMech ABI:

```c
int my_fn(const void **inputs, const int *sizes, int n,
          void *out_buf, int out_capacity, int *out_size) {
    /* unpack bytes from inputs[i]/sizes[i] by hand,
     * do the actual work,
     * pack result back into out_buf,
     * set *out_size */
}
```

That's project-specific boilerplate. The function can't be tested standalone, can't be linted by a normal C tool, can't be called by another non-SoraMech program. 307 wants the user to write what they'd write anyway:

```c
int classify(const char *text, int weight) {
    if (text[0] >= '0' && text[0] <= '9') return weight * 1;
    return weight * 2;
}
```

…and declare the signature in the box JSON:

```json
{ "id": "classify", "lang": "c", "ref": "classify.c", "fn": "classify",
  "inputs":  [{"name": "text", "type": "string"}, {"name": "weight", "type": "int"}],
  "returns": "int" }
```

The C spec then generates a wrapper `.c` next to the user's source, with a fixed entry point `sm_box_entry`. The wrapper unpacks bytes into typed C arguments per the JSON declaration, calls `classify(text, weight)`, serializes the return into the output buffer. The user's source stays pristine.

The same machinery unlocks **library functions as boxes**:

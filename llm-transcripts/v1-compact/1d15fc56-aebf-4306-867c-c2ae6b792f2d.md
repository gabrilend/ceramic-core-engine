**On how the loader knows sizes:**

The graph itself carries the answer for the known cases. Every box that produces a value writes down — in its metadata — what size its output is going to be. A box that always emits a 32-byte number declares 32. A box that builds a 4-megabyte image and knows it does, declares 4 megabytes. The loader reads every one of these declarations before the run starts, deduplicates them, and uses that list to set up its pre-warmed pools.

For the unknown case — an LLM call where the response could be 100 bytes or 100 kilobytes, a dynamic array whose length depends on input — the box just declares "size not known." When the loader sees that, it doesn't pre-warm a pool for that box; it knows the value will need to be allocated on demand when the box actually produces something.

Both kinds of value come out of the same underlying memory. The difference is just whether the loader had a pool ready for that size or not. A known-size value pops from its pre-warmed list — one step. An unknown-size value goes through a path that says "find me the smallest free region that fits, slice it if needed, give me back the front." Same allocator, two doors. The unknown-size door is slightly slower per allocation, but that cost is dwarfed by whatever produced the value in the first place (the LLM call itself, the array construction).

The case you raised — known-at-compile-time large allocation — is fully covered by the first door. There's nothing special about "large" here. The free-list approach treats a 4-megabyte size class no differently than a 32-byte size class; just a different list.

**On deterministic sweep triggers:**

Two natural moments. Both are decoupled from wall-clock time.

The first is the moment an allocation request can't be satisfied from any existing free-list. This is the obvious one — the system knows it's about to fail. Before it gives up and asks the operating system for more memory, it runs the sweep to consolidate any fragments that the cheap neighbor-merge didn't catch. If the sweep produces enough contiguous space to satisfy the request, the allocation succeeds and the heap doesn't grow. If it doesn't, only then does the system ask the OS for more. This makes the sweep the immediate alternative to heap growth — which is exactly when its work has the most value. It's also fully deterministic: same allocation pattern, same sweep moments.

The second is quiescence — moments when nothing is running. The runtime already recognizes these moments because it uses them to decide a run is complete. Between batches is a natural opportunity because no tasks are reading or writing chunks at that instant, so the sweep can be more aggressive without coordinating with anyone.

I'd start with just the first. It's the mandatory one — it's what stands between "allocation failed" and "ask the OS for more memory." The second is opportunistic and can be added later if profiling shows fragmentation is sneaking through.

A third option just to name it: trigger the sweep when the count of small free fragments crosses a threshold (an obvious sign of splintering). Deterministic, but needs tuning the threshold, and the first option covers most of the same ground without that work.

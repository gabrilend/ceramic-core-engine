Let me actually unpack the "Lua incompatibility" carefully, because I think I framed it too narrowly the first time.

**What the bridge contract says**

`lang_bridge_fn` is `(handle, src, src_size, dst, dst_capacity, dst_size)`. Bytes in, bytes out, with a handle on the side. That contract treats bytes as the universal medium.

**What Lua actually does inside the contract**

Lua's `native_to_json` reads from the top of `lua_State` and writes JSON to dst. It ignores src/src_size.
Lua's `json_to_native` parses src as JSON and pushes the value onto `lua_State`. It ignores dst/dst_capacity.

So Lua's bridge isn't byte-to-byte — it's value-on-stack-to-bytes and bytes-to-value-on-stack. The signature is the same; the semantics aren't.

**But this isn't actually a Lua-specific problem.**

The deeper thing is: Lua values don't have a canonical byte form. A Lua table has no fixed bytes — it's a hash table living in `lua_State`, and the only universal serialisation we picked was JSON. A Python `dict` would have the same problem. A Ruby hash, a JavaScript object, anything from a runtime that owns the value's lifetime — same. The byte-buffer assumption was always a property of "stateless byte-handlers" (C, Bash), not a property of "languages in general."

So if we want true agnosticism, the question isn't "how do we accommodate Lua?" — it's "does the system's contract assume buffer-orientation, and should it?"

**The fact that re-frames everything**

Look at what each spec's `invoke` actually does today on a JSON-tagged input:

- **Lua**: `parse_json_to_stack` → fall back to `lua_pushlstring` if parse fails. Already auto-detects.
- **C**: `try_strip_json_primitive` → fall back to raw bytes if parse fails. Already auto-detects.
- **Bash**: ignores the flag entirely; bytes are bytes for bash.

Every spec already does the "try JSON, fall back to native" dance internally. The `input_native[i]` flag is only an *optimization hint* that lets Lua skip the JSON parse attempt when dispatch knows the cell came from a same-language producer. It saves maybe 100ns per call on a same-lang Lua→Lua wire. It doesn't change semantics anywhere.

The `output_native` flag is similar — it tells Lua to use `tostring` when all consumers are same-lang. But that "fast path" is *broken* for tables (`tostring(table)` returns `"table: 0x..."`), so any honest Lua function that returns a table has to JSON-encode anyway. The flag is buying performance that mostly isn't usable.

**What dropping the flags really costs and buys**

Drop both flags and have every spec auto-detect:

- Cost: same-lang Lua→Lua pays a ~100ns JSON-parse-attempt-then-fallback per input. Lua→Lua with table returns starts working correctly (was broken). The "fast path" goes away.
- Buy: spec contract goes from `invoke(..., input_data, input_sizes, input_native, n_inputs, output_native, ...)` to `invoke(..., input_data, input_sizes, n_inputs, ...)`. Every future spec — Python, Ruby, anything — drops in without special-casing or runtime-class branching. The dual-ring slot's per-cell ring tag stops being load-bearing at the spec level (it's still useful for ordering).

**Where it really gets agnostic**

Once the flags are gone, the dual-ring slot itself becomes vestigial *for format purposes*. Its surviving job is ordering — the `RING_JSON` / `RING_NATIVE` tag was both "this is the format" and "this is the position in the producer sequence". The format part stops mattering; the position part still matters for parallel-iterator ordering.

We could either:
- **Keep dual-ring as-is**, with the per-cell tag becoming advisory/unused at the spec interface. Code stays, complexity stays in the slot store, but the spec contract is clean.
- **Collapse dual-ring back to single-ring tagged**, undoing slice 1. Bigger teardown, cleaner result.

**The honest summary**

The honest answer for the slot store this project uses:

**Lua doesn't interact with the shared memory at all, except as bytes.**

Each pool worker has its own `lua_State`. LuaJIT's hard rule is that a `lua_State` is owned by exactly one OS thread — you cannot touch it from another thread concurrently. The Lua GC heap (where tables, strings, closures live) is private to that one `lua_State`. So `lua_State` A on worker 0 and `lua_State` D on worker 3 have no shared Lua-level memory. They are, from each other's perspective, completely separate Lua universes that happen to be running the same source files.

What they CAN share is the project's byte-buffer layer:

- The slot store's cells (`slot_push` / `slot_pop` move bytes through ring buffers with per-slot spinlocks; the unified allocator refcounts the cells so they stay valid while any worker holds a reference).
- The large-value heap (the same refcount machinery, for variable-size payloads).

Both are managed at the C level. Workers read and write bytes; the spinlocks and atomics handle concurrency. Lua sees these only when its spec hands it a `(void *, int)` pair pointing into a cell, and Lua does one of two things with it:

- `lua_pushlstring(L, ptr, size)` — Lua copies the bytes into its own GC-managed string. After that, the slot cell can be released; Lua's string is independent.
- `parse_json_to_stack(L, ptr, size)` — Lua walks the bytes, constructs an equivalent Lua value in its own GC heap, pushes it. Same deal: after the call, the slot cell is decoupled from anything Lua holds.

In both cases, **the byte buffer's lifetime ends at the Lua call**. Lua never holds a pointer into a shared slot cell; it copies what it needs into its own state.

**LuaJIT FFI** is the one place this could be different. With FFI, Lua code can read shared memory directly via `ffi.cast(...)` without copying. We could expose slot bytes to Lua and let user code read them as a `cdata` pointer. But:

- The user's Lua function would have to call FFI explicitly. The wire-level contract still hands the spec bytes, not Lua values.
- FFI'd bytes are still bytes from Lua's perspective. You can't `pairs()` over an FFI pointer and get table semantics — Lua values are what live in `lua_State`'s GC heap, not in the C buffer.
- The slot cell's stable-address window (between alloc and unref) would have to extend across the FFI call's life, which is a real refcount discipline question.

**What the refactor actually does**

Today's dispatch action is two-phase:

  invoke spec

attempt task runs:
  if every required input is ready (slot has value, or read predecessor):
     snapshot inputs

- One task struct shape instead of two roles for the same struct.

- An attempt that finds inputs not ready returns without doing work; the next push to any of that consumer's slots triggers a fresh attempt.

**On malloc and shared memory**

`malloc` returns memory from the process heap. The process heap is shared across all threads in the process — that's a property of Linux's process model, not of malloc specifically. glibc's malloc is thread-safe via internal locking (or per-thread arenas with cross-arena access via locks for cross-thread reads). So a `malloc`'d pointer can be passed from worker A to the pool queue, picked up by worker D, dereferenced safely. That's what `dispatch_spawn` is doing today and it works.

So the current malloc IS in shared memory. The slab allocator from 302 is *also* in shared memory — it's a global pool with its own locks, just amortised across spawn/free pairs to skip the per-call malloc overhead. Both shapes work; slab is faster on hot graphs because it skips the malloc bookkeeping.

The "we need everything accessible from any thread" check is satisfied either way. Stack memory wouldn't be (it dies with the thread frame). Thread-local storage wouldn't be (per-thread). A single parent can have both. The pipeline iterates every box, decides per-box, runs the right transform.

**What the runtime does for each**

For `inline` boxes: nothing special. They're already flat in the compiled artifact; the dispatch sees ordinary boxes.

For `runtime` boxes: the map-language spec — `langs/map/spec.so` — implements the standard `lang_spec_t`:

- `map_init(worker_idx)`: empty cache of loaded sub-graphs.
- `map_invoke(handle, box, sub_map_path, fn_name, inputs, ..., out_buf, ...)`:
  1. Resolve the sub-map (cache key = path or runtime-supplied name). On miss, `graph_load(path)`, `graph_attach_runtime(...)` against a *fresh* per-worker slot store dedicated to this sub-graph instance.
  2. For each input, seed the matching marked external-`read` box's `cached_value` with the bytes the parent supplied.
  3. Drive the sub-graph to quiescence on the *same pool* — its tasks share workers with the parent. Per-task box ids get a nested-namespace prefix so traces stay distinguishable.
  4. Walk the `write` boxes, collect their captured outputs, pack into the size-indexed blob format, write to `out_buf`.
  5. Optionally reset slot state for re-invocation (cheaper than re-loading the whole sub-graph).

This is exactly Path B from 248's body, modular and self-contained.

**Where 313 sits in the picture**

- Inline-mode boxes contribute their source files to the parent's `__merged__.lua`. 313's existing merger handles them uniformly — it doesn't even need to know about encapsulation; it just sees more boxes after the inline pass ran.
- Runtime-mode boxes get their own `__merged__.lua` in their own compiled directory. 313 merges within each sub-map's region but doesn't cross the boundary.

**The schema constraint, which "both" doesn't escape**

Even in runtime mode, the parent needs to wire the encapsulating box's input ports and output channels at compile time. So the encapsulating box's JSON must declare the schema: input port names, output channel names, output blob layout. Sub-maps loaded at runtime have to *match* that schema (the spec checks at load time; mismatch is a fatal error).

This is like a function-pointer typedef in C — you can swap which function the pointer holds at run time, but the signature is fixed in source. For maps, the analogue is: the encapsulating box says "this sub-map will have inputs A/B/C and outputs X/Y," and any sub-map referenced by name at runtime has to satisfy that contract.

**Cost summary, honest**

- The map-language spec is built either way (it's the foundation for runtime mode and the dynamic-load case is your stated motivating use).
- Inline-mode is a graph-rewrite step in the compile pipeline. Probably 100–200 lines of clean code: load the sub-map, namespace, splice, recurse. Lives in `soramech-compile.sh` or a sibling.
- The encap_mode flag is one field in the box JSON, one branch in the rewrite pass, one branch in the dispatch's "is this a real call or a runtime sub-graph?" decision (and the latter is just "what spec answers this `lang`").
- Output packing/unpacking is the same helper library either way (used at the boundary in runtime mode, used at the inlined `write`-replacement in inline mode if the user wants the blob format).

So "both" is roughly **Path B's work plus a graph-rewrite pass for Path A's transform**. It's bigger than either path alone, but the *runtime* surface area is just Path B's spec; everything Path A adds happens at compile time and disappears before the runtime sees the graph. That separation keeps "both" from compounding complexity at the hot path — the dispatch loop never branches on `encap_mode`.

**One last thing worth surfacing**

If `encap_mode` is a per-box choice, the user can mix freely in one parent. Stats-pipeline as inline (perf-critical, known at compile time); user-template-loader as runtime (dynamic, hot-reloadable). The semantics are the same from the parent's perspective — both look like a call box with declared inputs and outputs. The difference is invisible to the parent's other boxes; it only shows up in build output (one is gone, one stays) and in the runtime profile (one calls inline, one calls through the map spec).

That clean separation — "both modes look the same to the rest of the parent" — is what makes "both" cheaper than it sounds. The encapsulating box's *contract* is the same; only the implementation behind it varies.

**246 in short**

A per-input-port shim the user writes — runs before the consumer's `invoke` sees the value, intercepts raw bytes plus the `which_ring` tag, and produces translated native bytes the spec then receives as if the default decode had produced them.

Two distinct motivating cases — and you can see why they share the same mechanism:

- **Cross-language ambiguity**: a C++ class arriving at a C box, a `void *` carrying a libcurl handle, a tagged union whose discriminator is on a separate port. JSON's structure can't carry these losslessly; the user has knowledge the spec can't ever infer. Per-port shim is where that knowledge lives.
- **Same-language user transformation**: a C box emits a float; the next C box wants it truncated-then-rounded. Or degrees → radians on one port. Or clamp-to-range. No language boundary, just user semantics that don't belong in the box's main function.

**The principled choices behind the design**

- **Per-port, not per-box.** Each port carries one kind of value; only the weird ports get shims. A box with three string inputs and one C++ class input writes one shim, not four.
- **Input-side only.** A producer's spec always knows how to serialise its own language's values — full reflective access to its own type system. Reading is the asymmetric direction: the receiver can't infer what the sender meant by an opaque pointer. So shims live where the ambiguity is.
- **Shim's output is always treated as native by `invoke`.** The shim does the decode; the consumer's main function sees native bytes, same as if a same-language producer had pushed them.

**Where it sits architecturally**

Slots into the existing dual-ring shape from 312. The shim sees both the raw bytes AND the per-cell `which_ring` tag, so it can branch on "this is JSON from cross-lang" vs "this is native from same-lang" inside the shim. The default decode runs when no shim is attached — nothing about the existing fast path changes.

Composes with 313's merge: translation files are just another function in the same-language merged module.

Composes with 245's wire-colouring (the goldenrod-cheddar colour activates automatically once a port has a custom translation attached — visual marker that this wire is non-default).

**Status, honestly**

Open. No implementation. Nothing blocks it:

- 312's dual-ring is in place (shim's `which_ring` argument has its source).

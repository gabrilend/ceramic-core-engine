# Q1 — Datapath walk

Let me lay out every term, then trace the path a `create_box` call takes through the runtime, and show **exactly where the existing invariant snaps**.

## Vocabulary (the things on the diagram)

- **Box** — one node in the graph. On disk: a JSON file at `boxes/<id>.json`. At runtime: a small durable record holding its language handle (e.g. a `lua_State` slot), its input port slot indices, and its output edge list.

- **Input port** — a named position on a box where values arrive. A box may have many. Each port owns exactly one **slot**.

- **Output** — a single value-producing position. **One per box** (issue 218). Fan-out is achieved by having multiple wires *leave* the one output.

- **Slot** — a ring buffer (or atomic counter) belonging to one input port. The receptacle a producer's value lands in when a wire is "pushed." Five variants per the header you just saw: 1-cell peek, N-cell pop, N-cell pop tagged, atomic counter, large-value.

- **Slot store** — the pool that holds all slots for the whole graph. Allocated once at **graph load**. Per-slot locks on the hot path; **no allocator-wide lock**. That last clause is the load-bearing one for Q1.

- **Graph load** — the moment, before any task runs, when the C runner reads every `boxes/<id>.json`, builds the in-memory box records, counts how many slots each box's input ports need, and asks the slot store to allocate them all at once. After this finishes, the slot store's size is frozen.

- **Dispatch layer** — the worker-side state machine. When a value lands in a box's last empty input slot, the dispatcher spawns a **task** for that box. The task pops its inputs, invokes the spec, pushes the output into downstream slots, ends. Then it spawns more tasks for the now-ready downstream boxes.

- **Task** — ephemeral. One execution of one box on one worker. Tasks carry just `box_id` + a counter snapshot; everything else lives in the durable box record and the durable slots.

- **Worker** — a thread in the C pool. Workers pull tasks off the pool's queue.

- **Spec** — the language plugin (`langs/<name>/spec.so`). The thing the dispatcher calls when it's time for a box to actually compute. The spec's `invoke()` is where user code runs.

- **Built-in** — a function the runtime exposes *into* a spec's invocation context. `create_box` and `connect` would be built-ins: callable from inside a running spec, implemented by the runtime in C.

The **breakage point** is step 4: the slot store was built with the assumption that its size never changes after graph load. The header literally encodes this: "Lifetime is the run. Slots are freed when the store is destroyed at the end of the run." There is no `slot_grow` primitive, and the per-slot locking strategy was chosen *because* the slot **array** itself never moves — once a slot's index is handed out, the pointer to it is stable forever, so readers can cache the address.

If the array can grow, two things go wrong:
- **Reallocation moves slots.** A `realloc`-style grow invalidates every cached slot pointer that any worker is mid-write on.
- **The lock-free hot path becomes lockful.** Adding even a single rwlock around the slot array to protect grow-vs-access kills the "no allocator-wide lock" property the header is bragging about.

## The three options, against the break

**(a) Runtime growth — let the slot store grow in place.** Means redesigning the slot store's storage so slot pointers stay stable across growth (e.g. a two-level table: chunks of N slots each, append a new chunk to grow; old chunks never move; readers index by `chunk_idx, slot_in_chunk`). The hot path stays lock-free *if* you accept that "what slots exist" is observed via an atomic counter that workers re-read. Implementation cost is real but bounded; conceptual cost is that *every* runtime structure that the dispatcher walks (edge lists, box records) needs the same treatment. The user pays nothing at the API; the system grows a lot of concurrency machinery.

**(b) Build-time only — `create_box` runs during graph load, not during dispatch.** The built-in is callable, but only from a special "graph build" phase before any task runs. A planner box that wants dynamic structure has to declare every possible sub-graph statically with conditional connections (which already exists via comparator branching). Cheapest for the runtime; effectively says **self-construction isn't really self-construction** — it's just code-driven graph authoring at startup. The user loses "the planner box decides what to build at runtime" entirely.

**(c) Sandboxed dynamic region — a second slot store for new boxes.** Original graph's store stays frozen, lock-free, untouched. New boxes from `create_box` go into a separate growable store. Edges from static-into-dynamic and dynamic-into-dynamic are allowed; edges from dynamic-into-static are forbidden (because that would require pushing into a static box's slot from an unknown-at-load-time producer, which breaks compile-time slot sizing). The dispatcher gains a "which region?" lookup before every push, paying a small constant cost. Conceptually clean: the part of the graph that knew about itself at compile time stays the way it was; the part that grew at runtime lives in its own world.

`★ Insight ─────────────────────────────────────`
The split between (a) and (c) is the same split you see in OS kernels between "monolithic allocator" and "per-arena allocator." (a) generalizes the existing thing to handle the new case; (c) puts the new case in its own room so the old thing stays simple. Soramech's existing rule "boxes are durable, tasks are ephemeral" already chose the per-arena flavor at the *task* level — (c) extends that same philosophy one level up to the *box* level.
`─────────────────────────────────────────────────`

**The way the three options frame the use case:**

- (a) says *the runtime adapts to dynamic structure.*
- (b) says *dynamic structure isn't really runtime; bring it back to load time.*
- (c) says *static and dynamic are different beasts; let them live in different houses.*

## "Allocator-wide lock" — the thing we are *not* paying for

Imagine the slot store had **one mutex** at the top, and every `push` and every `pop` from any worker on any slot had to grab it. Worker A pushing to slot 5 would block worker B popping from slot 99 — totally unrelated operations, serialized. That's an allocator-wide lock. The slot store explicitly avoids it by giving each slot its own tiny lock (a one-byte `atomic_flag` spinlock) for header mutation; the global pool has no lock at all on the read/write path. Throughput therefore scales with the *number of slots being touched at once*, not the number of workers, which is the property that makes the C pool worth building. Anything we add for dynamic growth has to preserve this — that's the constraint Q1 was really probing.

## "Counter snapshot" — the iterator-ordering tag

When an **iterator box** spawns tasks (it's the kind that fires repeatedly, once per element of some sequence), every task gets the iterator's counter value frozen at spawn time. Two reasons it travels with the task:

1. **The dispatch layer needs to know which "iteration" this task represents** when it pushes the output downstream. If the consumer slot is in `SLOT_TAGGED` mode (from the header), the push attaches this counter as the cell's tag, and the consumer pops in iterator-counter order rather than arrival order. This is how parallel iterator tasks can run out-of-order across workers but the downstream box still sees them in iteration order.
2. **For comparator/randomizer routing decisions**, the counter snapshot lets the task make a deterministic per-iteration choice (e.g. randomizer with a seeded PRNG keyed off the counter).

So it's not just an integer — it's the **task's identity within its parent box's iteration sequence**, used both for downstream ordering tags and for any per-iteration routing the dispatcher does.

## Your two-level table design — does it solve Q1? Mostly yes, with one subtlety

Your intuition is exactly right: hold pointers in an index table, and the slots themselves never move. The thing I want to make explicit is that **the table itself also needs to grow without moving**, or readers cache a stale table pointer:

```
 [ index table — chunked, append-only ]
   chunk 0: [ s0* | s1* | s2* | ... | s63* ]
   chunk 1: [ s64* | s65* | ... | s127* ]
   chunk 2: [ s128* | ... ]                   ← new chunk appended on growth
       ▲
       │ slot_idx 5 lives at chunk[0][5]
       │ slot_idx 200 lives at chunk[3][8]
       │
   workers read this concurrently while writers append new chunks
```

The two-level shape is what makes this safe lock-free:

- **Slots themselves**: never move, ever. Once allocated, the pointer is stable for the run.
- **Index table top level**: a small array of chunk pointers. Adding a chunk writes a single pointer slot at the next free top-level index, then bumps an atomic "chunks in use" counter. Readers re-read the counter on lookup. No realloc, no copy, no movement.
- **Within a chunk**: also append-only. Workers atomic-increment a per-chunk "next free slot index" to claim a slot during `create_box`, then publish the slot pointer at that index.

Cost per access: one extra indirection (read the chunk pointer, then the slot pointer). One extra cache line if the chunk pointer isn't already in L1. That's the price for collapsing static and dynamic into one mechanism, and it's small enough to pipeline away.

`★ Insight ─────────────────────────────────────`
This is the **same shape Linux uses for its file descriptor table** (per-process FD table, grows as new FDs are opened, FD numbers stay stable forever, lookups are O(1) with one indirection). The pattern is general because it satisfies one specific requirement: "handles must stay stable under concurrent growth." Anywhere that requirement appears, this two-level chunked-append structure is a reliable answer.

## "Double-buffered ring-buffer" for the index table — checking what we're solving

Want to make sure we're talking about the same growth event before picking machinery. Two candidates, very different shapes:

**(A) Index table growth** — the top-level structure that maps "slot index N" to "this slot lives at address X." This grows when new boxes are added.

**(B) Individual ring buffer growth** — a single input port's cells, when the user pushes 200 values before the consumer fires.

Double-buffering — allocate a new larger version, copy contents, atomically swap a pointer, wait for old readers to drain, free the old — is a **real and robust pattern** (it's the core idea behind RCU in the Linux kernel). It's the right answer for **(B)** the individual ring buffer growth, because each slot already has its own lock, and growth happens under that lock: take the lock, allocate new ring, copy cells, swap, release. Old readers can't exist because they couldn't have held the lock concurrently. Clean.

For **(A)** the index table, double-buffering works but is overkill — we'd be paying for the copy on every growth event when we don't have to copy at all. The chunked-append shape I described skips copying entirely:

```
top-level array (sized large at startup, e.g. 1024 slots)
   ┌─────────────────────────────────────────────────────┐
   │ chunk0* │ chunk1* │ chunk2* │ NULL │ NULL │ ... │   │
   └─────────────────────────────────────────────────────┘
       │         │         │
       ▼         ▼         ▼
     [64 slot ptrs]  [64 slot ptrs]  [64 slot ptrs]

growth = "write a chunk pointer to the next NULL top-level slot,
          bump the atomic chunks-in-use counter"
no copy, no swap, no drain.
```

Chunked-append is more robust *for this case* because there's no swap-and-drain race surface at all — readers see either old size or new size, and any size they see is valid. The user pays one pointer indirection per slot lookup forever.

## The audit fix — VLA or per-worker scratch

**`[16]` inputs (dispatch.c:804+, 863+):** five parallel stack arrays — `bufs`, `buf_chunks`, `datas`, `sizes`, `input_native` — populated by `read_inputs()`, freed by `release_inputs()` at the end of the call. Better than I feared: the code does check `n > 16` and returns -1, so it's a *hard error* on a 17-input box, not silent corruption. But it's still a cap on what `create_box` will be able to make.

Three options, in increasing weight:

- **(i) VLA:** `char *bufs[n];` — C99 variable-length arrays. Zero allocator calls; the stack pointer just moves by `n * 5 * sizeof(void*)`. The only risk is blowing the stack on pathological `n` (a box with 100k inputs), and we can keep the existing `n > some_huge_cap` guard purely as a sanity check (say 4096). Cheapest possible.
- **(ii) Per-worker scratch arena:** worker context grows a reusable buffer; this call bumps a pointer to claim 5×n slots, resets the bump pointer at call end. One alloc-on-grow per worker per peak-size-ever, zero per call. Pays for itself if VLA stack pressure ever shows up.
- **(iii) Per-call malloc:** five allocs and frees per invocation. Real cost on hot paths. Worst of the three.

Recommendation: **(i) VLA**, with the existing sanity-cap kept (at, say, 4096) so a runaway loader doesn't get a stack-overflow segfault. Promote to (ii) only if profiling ever shows VLA stack pressure — for normal box widths (1–20 inputs) the cost is unmeasurable.

**`branch[24]` (dispatch.c:629, 647, 678, etc.):** these format `"out_%u"` for branch names. Worst case is `"out_4294967295"` = 14 chars + null = 15 bytes. Cap of 24 is **artificially low but never reached**, and `snprintf` truncates safely. Not a real bug — just hygiene. Easiest fix is to make it a named constant (`MAX_BRANCH_NAME = 16` or so, compile-time proven sufficient) so future format-string changes have a single place to update. Not worth a deeper rework.

- **C:** the verbose case. Three options ranked:

- **Bash:** JSON strings. `soramech_connect '{"from_box":"a","to_box":"b","to_input":"x"}'`. Bash has no native dict; JSON strings are how it talks to everything anyway.

## "We output box return values to JSON sometimes. Could we use that machinery somehow?" — Yes, the *same* machinery

```
[user spec code]                 [language spec]              [runtime]

    to_input = "x"                                              instantiate
  }                                                            connection
  soramech.connect(spec_table)
```

- **No new callback** needed on the language spec. `native_to_json` is already there.

- **One validator** in the runtime: the box JSON schema validator already exists for `boxes/<id>.json` files at graph load. Reused as-is for runtime-constructed boxes.
- **Persistence is trivial.** If `create_box` ever wants an "also write this to disk" option, it has the JSON in hand — `fwrite` to `boxes/<id>.json` and you're done.

The machinery you sensed should be reusable IS reusable. Same callback, same JSON, same validator, same on-disk format. The whole thing collapses to "things in SoraMech are JSON; languages convert their native shapes to JSON; everything downstream consumes JSON."

## What I did

`runtime_create_box` and `runtime_connect` are language-agnostic C functions in `src/018-runtime-builtins.c` — those are fine. But to make them *callable from user code*, I exposed them as **Lua functions** (`soramech.create_box`, `soramech.connect`) registered in `langs/lua/spec.c`. The plan for 319e was to repeat the same wrapping in `langs/c/spec.c` and `langs/bash/spec.c`.

That repetition-per-language is the smell you're spotting. Read boxes and write boxes don't get re-implemented per language — they're **box kinds** in the JSON schema, handled by the runtime itself (`do_write_box` in dispatch.c), and user code interacts with them by wiring data in and out.

## What I should have done

Make `create_box` and `connect` **new box kinds**, alongside `read` / `write` / `call` / `comparator` / `iterator`:

```json
{ "id": "spawn_step", "kind": "create_box",
  "inputs": [ { "name": "spec", "type": "json" } ],
  "connections": [ ... wire the resulting id somewhere ... ] }

{ "id": "wire_it",   "kind": "connect",
  "inputs": [ { "name": "from_box", "type": "string" },
              { "name": "to_box",   "type": "string" },
              { "name": "to_input", "type": "string" } ] }
```

Then a Lua box (or C box, or Bash box) wanting to spawn a downstream pipeline just:
1. Outputs a JSON spec on its wire
2. The spec flows into a `create_box` kind box
3. The `create_box` box outputs the new id
4. The id flows wherever it's needed (probably into a `connect` box)

**Same machinery for every language. Zero per-language bindings.** Matches the rest of SoraMech's "the language spec writes data, the runtime moves data, special box kinds do special things" model.

## Tradeoff to flag

There's one thing the box-kind model handles differently from the in-spec-callback model: **getting the new box's id back to the creator synchronously**. With Lua bindings, the planner calls `create_box(spec)` and gets the id on the next line. With box-kinds, the planner outputs a spec, fires once, and the id arrives back via a wire later (potentially in the next iteration).

For most use cases this is fine — the dataflow shape is natural and async anyway. For some patterns it's awkward, e.g. "create N boxes in a loop and remember all their ids." But those patterns can still be expressed via iterator-style boxes or via batching the spec into an array, so I don't think it's load-bearing.

Here's how it works, walking from outside in.

**The contract is one C struct.** `langs/lang-spec.h` declares `lang_spec_t` — a struct of function pointers. A language spec is "an instance of this struct, compiled into a `.so`, dropped at `langs/<name>/spec.so`." That's the whole interface. Anyone adding a language fills the struct out and ships the directory.

The fields in order of when they fire:

```
init(worker_idx)        — at pool startup, once per worker thread.
                           Returns an opaque handle the spec wants
                           to carry around (Lua's lua_State, C's
                           dlopen cache, Bash's persistent socket).
compile(src, out)       — optional. For languages that need a build
                           step, called once per source file. C
                           runs gcc -shared -fPIC. Lua and Bash
                           leave this NULL.
invoke(handle, file, fn,
       inputs, sizes, n,
       out, cap, *out_size)
                        — per box call. The runtime hands you bytes
                           in, you write bytes out.
teardown(handle)        — at pool shutdown, per worker.
```

Plus a few fast-path / bridge callbacks from 312 (`invoke_native`, `invoke_json`, `native_to_json`, `json_to_native`) that are optional — leave them NULL and dispatch falls back to the canonical `invoke`.

**Discovery happens at startup.** `src/011-spec-registry.c` scans `langs/*/`, `dlopen`s each `spec.so`, reads the exported `soramech_lang_spec` symbol (the struct), and builds a name-and-extension-keyed lookup. The pool runner consults that registry per-worker to call `init`. The dispatch layer consults it per-task to call `invoke`.

**How "what you define" turns into the call — today.** This is the part the existing implementation does the *least* automatic glue for. Three pieces:

1. **The spec author writes plain C.** No glue generation. They write `static int my_invoke(...)` and assign it to `.invoke = my_invoke` in the exported struct. Same for `init`, `teardown`, etc. The "spec" *is* the hand-written C file.

2. **The box author follows a per-language convention.** This is where you'd expect glue and where there mostly isn't any yet:
   - **Lua box**: write a file that does `local M = {}; function M.foo(a, b) ... end; return M`. The Lua spec's invoke pushes each input as a Lua string, calls `M[fn_name](...)`, and writes the return value back out. The convention is "return a table."
   - **C box**: write a function with this *fixed signature*:
     ```c
     int my_fn(const void **inputs, const int *sizes, int n,
               void *out_buf, int out_capacity, int *out_size);
     ```
     The signature matches the spec's `invoke` shape minus the per-worker handle. Compile-time, the spec's `compile` runs gcc on the file; invoke-time, it dlsyms the symbol and calls it. **No wrapper generation today** — every C box reads its bytes by hand.
   - **Bash box**: a function `my_fn() { ... }` in a `.sh`. The Bash spec's invoke runs the function via a persistent socketpair (issue 308) and reads stdout.

3. **The glue is the `invoke` callback itself.** That callback's body is the user-facing translation layer between "bytes on a wire" and "a call into the language." Each language's spec.c hand-codes it. For Lua: push, call, tostring, copy. For C: dlsym, call function pointer, return. For Bash: serialize, send over socket, read.

**Where "generated glue" *will* matter — the typed wrapper from 307.** This is the piece that doesn't exist yet but is the natural next move. The C spec's comment calls it out (langs/c/spec.c lines 16–19): "does not generate per-box wrappers from declared signatures (issue 307's optional advanced mode) — every C box uses the fixed signature above." The vision is:

- The user writes `int my_add(int a, int b) { return a + b; }` — a plain C function with declared types.
- A build step generates a wrapper file: `int my_add_wrapper(const void **inputs, const int *sizes, int n, void *out_buf, int out_cap, int *out_size) { int a = *(int*)inputs[0]; int b = *(int*)inputs[1]; int r = my_add(a, b); *(int*)out_buf = r; *out_size = sizeof(int); return 0; }`.
- The user never sees the wrapper.

That wrapper file is the only place "glue" gets *generated* in the design as drafted. Everywhere else, the glue is hand-written inside the spec's `invoke`. And the wrapper-generation step itself is also hand-written in the C spec — the spec's `compile` callback would emit the wrapper from a signature it parsed from the source.

**Where 217's variadic-detection fits.** Two layers, neither of which involves code generation:

- **Editor side (issue 231)**: `langs/<name>/parser.js` exposes `parse_function_signature(source, fn_name)` returning `{inputs, variadic_inputs, ...}`. The editor's file browser and inspector consume it. This is pure JavaScript ES-module per language; no C, no runtime, no glue.
- **Runtime side (already works)**: the spec's `invoke` receives `n_inputs` and `inputs[]` of whatever length the dispatch layer assembled. For Lua's `function M.foo(sep, ...)`, the spec pushes all N as Lua values and the `...` collects the tail naturally. For Bash, `"$@"` does the same. For C with the fixed-signature convention, `inputs[]` is just an N-element array — the user's box function reads as many as it cares about.

So **adding a new language is one directory:**

```
langs/python/
  spec.c          ← lang_spec_t with init/invoke/teardown for Python
  Makefile        ← builds spec.c into spec.so against libpython
  parser.js       ← parses def fn(*args): … and tells the editor
```

The runtime sees the new `spec.so` at startup and registers it. The editor sees the new `parser.js` and uses it for `.py` files. The user never edits the editor or the dispatch layer.

For the variadic-correctness question: it's purely editor-side.

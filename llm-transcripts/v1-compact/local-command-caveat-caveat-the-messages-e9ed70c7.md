## Unions — not a tuple

A tuple is a *product type*: all fields exist at once, each at its own offset. A C `struct point { int x; int y; }` is a tuple — `x` and `y` both live, both readable.

A union is a *sum type*: all fields share the same bytes. Only one is "live" at a time. The classic shape:

```c
union value { int i; float f; char *s; };  /* 8 bytes, one of three meanings */
```

You write `v.i = 42`, then read `v.f`, and you get the float interpretation of `0x0000002a` — garbage, because you reinterpreted the bytes. Unions are almost always paired with a discriminator field that says "which variant is currently live":

```c
struct tagged {
    enum { INT, FLOAT, STR } tag;
    union { int i; float f; char *s; } v;
};
```

The reason this matters for serialization: a bare union has no way to tell you which variant to serialize. Three different fields lay claim to the same bytes. Without a discriminator we'd have to pick arbitrarily. With a discriminator we're fine — read the tag, serialize that variant.

So at the spec layer, bare unions become another "user provides a rule" case — same shape as length-unknown pointers. The rule says either "field X is the discriminator" or "this union is always variant Y in this context." The system never guesses.

## The core design — handles as the universal fallback

Your push to make this language-agnostic with no special cases reframes the whole thing. Let me state what I think you're actually proposing, because it's a cleaner design than what I had:

**Every value in every language factors into exactly one of two cases:**

1. **Decomposable.** The spec can break it down into a tree of primitives (numbers, strings, bytes, bools, plus ordered lists and named records and tagged variants). Round-trips natively to any other spec.

2. **Handle.** The spec can't (or won't) decompose it. Instead it emits a *handle* — a tiny primitive token (an id string plus a list of operations it supports). The handle crosses the wire. The underlying state stays in the originating language. When some other language wants to act on the handle, the runtime routes the operation back to the owning spec.

That's the whole serialization rule. No third case. **Nothing is unserializable, because the worst case is "this becomes a handle."**

A Lua coroutine? Handle. The Lua spec owns the coroutine; the handle says `ops: ["resume","status","close"]`. C never sees the call stack — it just calls `invoke_handle(id, "resume", args)` and the runtime dispatches back to Lua.

A C function pointer to unknown code? Handle. The C spec owns the pointer; the handle says `ops: ["call"]` plus the signature (if known). Lua never dereferences — it asks the runtime to invoke, and the C spec does the actual call.

A C pointer-to-opaque-struct? Handle. The struct stays on the C heap. C-side accessors are the `ops`.

This works because *no language ever has to understand another language's exotic types*. Every spec only ever sees primitives, composites of primitives, or handles. Handles are also primitives (just a string id with op metadata). The spec interface is uniform.

## Teaching the system to decompose

The handle is the safe default. But sometimes you *want* a type to be transparent — you want a Lua userdata to flow into C as a real struct, not as an opaque token. That's where user-written rules come in:

Each spec exposes a **rule registry**. The user writes rules in the spec's own native form (Lua rules for Lua types, C rules for C types) and registers them. A rule says "for values of type T, here's how to decompose to a tree, and here's how to rebuild from a tree." Once the rule exists, the spec's `to_tree` uses it instead of falling back to a handle.

This means:
- The Lua spec ships with built-in rules for the easy types (number, string, table-as-record, table-as-list).
- The user writes rules for their own exotic types (a custom userdata class, a coroutine they want decomposed into call-stack metadata).
- The C spec ships with rules for primitives, structs, arrays, length-tracked pointers.
- The user writes rules for the awkward C cases (length-unknown pointers via a length hint, unions via a discriminator hint, opaque pointers via accessor functions).

The Lua spec doesn't know what C does. The C spec doesn't know what Lua does. Both produce the same tree format, both consume the same tree format. The runtime is dumb glue.

## Conceding handles

The argument that broke it for me: a real library function (`qsort`, `pthread_create`, anything from libc) expects a real native value. ## What the design actually is

Every value, no matter how exotic, decomposes to a tree of primitives. That tree is the wire format. The destination spec reconstructs the value as a real native value of whatever type its declared input signature says — *including* synthesizing native executables (trampolines, FFI bridges) when the destination expects something callable.

The wire only ever carries data. The "handle"-shaped thing — a callable pointer whose body routes calls back to the originating worker — is reconstructed *at receive time* by the destination spec, transparently. From the library function's perspective: it sees a normal function pointer. From the wire's perspective: it carried `{address_in_source_worker, signature, owner_worker_id}` as primitives. The destination C spec's reconstruction step, given that tree and the declared C type "function pointer with signature (int,int)->int", emits a libffi-generated trampoline that, when called by qsort, marshals args back across to the originating worker. The trampoline IS the reconstructed value.

Same trick for Lua coroutines into C: the source Lua spec decomposes the coroutine into its parts (bytecode of frames, locals, upvalues, status, pc) — pure data. If the C box's input signature is `struct lua_frame[]`, the C spec walks the tree and fills the struct. If the C box's input signature is "callable that returns next value" — C spec emits a trampoline that ships resume calls back to the source Lua worker.

What this means: **every concrete value the user wires up is a real, callable, dereferenceable, native value in the destination language.** The wire is just bytes; the destination spec does whatever it needs to make those bytes into the native form its signature demands.

## What the null-in-array case implies for the bridge

It's a load-bearing finding, not a curiosity. The wire format (JSON) carries strictly more shape than any one host language. Lua loses `null` inside sequences. C will lose JSON's tag-free number when it can't tell int from double without a type declaration. Bash will lose nested structure unless we mandate JSON-formatted output.

So the bridge is **not symmetric per-spec** — a value entering Lua-side may not come out structurally identical on the other side. This forks the design into two stances we need to pick between:

1. **Lossy round-trips are the box author's problem.** Same-language wires (issue 312) stay lossless; cross-language wires go through JSON and the user is told at wire-compile time when the source language can express something the destination can't. We add a compatibility check at graph-load (e.g. "Lua → C edge: target type `int[]` cannot contain null — your Lua data box returns an array with nil") and otherwise accept the limitation.

2. **The bridge invents a per-language convention to preserve JSON faithfully.** For Lua specifically: arrays carry an explicit `{n=3, [1]=true, [2]=false, [3]=nil}` shape; the bridge encodes/decodes around the `n` field. Heavier; intrudes on idiomatic Lua; but every value survives a round-trip.

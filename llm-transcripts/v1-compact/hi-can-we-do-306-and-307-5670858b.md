**Refined version:** the slot has only *two* rings. One native ring for "bytes in the consumer's language" and one JSON ring for "bytes from anyone else." Now same-lang producers write native to the native ring (zero translation), cross-lang producers translate-to-JSON on the way in and write to the JSON ring (one translation, exactly as today), and the consumer pops the ordering ring to know which ring to read from next. That refined version is actually strictly better than the per-port-classification thing I was about to code. The per-port version is pessimistic: if any one producer feeding a port is cross-lang, the *whole port* goes JSON, and the same-lang fan-in producers eat translation cost they didn't need to. The two-ring version keeps the same-lang producers native even when a cross-lang sibling is feeding the same port. Precision goes from per-port to per-cell.

Cost is a constant factor — one extra pointer indirection on pop, one extra `which_ring?` decision on push, two ring buffers' worth of memory per slot instead of one. Cheap.

The interesting question is when this actually matters. For a port with no cross-lang producers, both designs are identical (everything stays native). For a port with only cross-lang producers, both are identical (everything's JSON). The win is on **mixed fan-in** — a port that some same-language box and some cross-language box both feed. Probably uncommon in the grand scheme, but free correctness is free correctness.

**Sentinel mechanics, walked through your function-pointer example.**

C box produces `int compare(void *, void *)`. The box JSON declares the output type as a function pointer with that signature. The C spec's `native_to_json` recognizes "this isn't a JSON-shaped value, it's a callable" and emits:

```json
{"$function_pointer": {"addr": "0x7fffabcd1234",
                       "signature": "int(void*,void*)"}}
```

The Lua consumer pops the JSON. Its `json_to_native` sees the `$function_pointer` sentinel and reconstructs the callable using **LuaJIT FFI** — code the Lua spec author wrote once:

```c
// Pseudocode inside lua_json_to_native when it sees $function_pointer
lua_getglobal(L, "ffi");
lua_getfield(L, -1, "cast");
lua_pushstring(L, signature);   // "int (*)(void*, void*)"
lua_pushinteger(L, addr);
lua_call(L, 2, 1);
// Stack top now holds an FFI callable Lua can call like a Lua function
```

The Lua box's user code then calls it normally — `compare_fn(a, b)` — and LuaJIT FFI does the actual C call. **In-process only**, because the address is a raw memory pointer that's only meaningful in this process.

No auto-generation in the general case. The spec author writes the reconstruction once per sentinel kind per language. For Python (hypothetical): `ctypes.CFUNCTYPE(...)`. For Bash: no FFI capability, so a wire carrying a function pointer to a Bash box **fails at compile time**. That's the "compile error if a cross-language wire ever points at a language that can't reconstruct" half of the design.

**`$ref` for large datasets** works the same shape, simpler:

```json
{"$ref": {"ptr": "0x...", "len": 1048576, "type": "bytes"}}
```

The bytes live in the large-value heap (`src/015-large-value-heap.c`). Refcount = number of consumer slots. Lua reads with `lua_pushlstring(ptr, len)` (copies into Lua's heap). C uses the pointer directly. Bash via UDS — the marshaller inlines the bytes at the socket boundary, since cross-process can't share a raw pointer. The user never knows it's a reference unless they care; it just looks like a value.

**`$lang_opaque`** — a tagged blob the producer's language wraps around a value it can't structurally describe (a Lua coroutine, a Python generator). The consumer either knows what to do (same language family) or wire compile fails. This is the catch-all when `$ref` and `$function_pointer` don't fit.

**The flexibility-vs-performance question — honest answer:**

It's not "huge flexibility cost recovered by threading." Threading is orthogonal parallelism, not a per-cell-cost reduction. The cost story is **paid per edge, where it actually occurs:**

- Same-language native wires: bytes pass through, no translation. Native ring of the slot.
- Cross-language wires: JSON encode + decode at the boundary. JSON ring of the slot. Bounded by value size.
- Sentinels: tiny — a few dozen bytes of JSON wrapping a pointer. The reconstruction is `ffi.cast` or equivalent: nanoseconds.
- Custom shims: whatever the user writes. Could be one line or could be a parser.

The "flexibility" doesn't impose a uniform tax. Primitives and structured data flow at JSON-parse cost across borders; same-language stays native; in-process references flow at pointer-copy cost via sentinels. Threading adds throughput on top by running boxes concurrently — but it doesn't make a JSON parse faster, it just lets two of them happen at once on different cores.

The real long-term optimization isn't threading-recovers-cost; it's **313's same-language merge** thinning the spec-invocation overhead inside same-language regions (no dlsym + marshal + bridge per call; the merged module is one big function pile and calls are direct). That's where the structural perf win lands, and it stacks cleanly on top of the dual-ring design.

The layering, made concrete in one box invocation under both 312 and 313:

```
1. Worker picks up the task.
2. Dispatch reads inputs from the box's slots.        ← 312 (dual-ring slot)
3. Dispatch decides which function to call.
   - Default: look up spec by box->spec_idx, call its invoke
   - 313 merged region: function is already a known callable
     in the merged module; direct call.
4. Function runs, returns a value.
5. Dispatch writes output to consumer slots.          ← 312 (per-edge ring routing)
```

Steps 2 and 5 are 312's territory and are unchanged by 313. Step 3 is where they differ. The slot machinery stays alive in the merged region because tasks are still scheduled across worker threads — a producer on worker 0 and a consumer on worker 1 still need the slot to hand off the value. 313 doesn't collapse parallelism; it just makes the per-call overhead near-zero for in-region calls.

**What this unlocks.**

A Lua-to-C wire now actually carries JSON across the boundary, in both directions:

- Lua returns the number `10` → the wire carries `10` (the JSON encoding) → C unwraps it (no-op, already in the right form) → the C function reads `10` like a number.
